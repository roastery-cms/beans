## [Unreleased]

### Added

- **`onError`, a new standard (TC39) method decorator in `@roastery/beans/domain/entity/decorators`.** Joins `beforeHandle`/`afterHandle` as the third method decorator, but is the first in the pillar to introduce a `try`/`catch`: it wraps the decorated `Entity` method, and if it throws, builds an event from the caught error, `raiseEvent`s it, then **always re-throws the original error** — the decorated method's observable behaviour is unchanged for its caller, the event is a side channel only, never a way to swallow a failure. Accepts **either** a `BareDomainEventClass` (`@onError(SomeEvent)`, the same payload-less form the other four decorators take — reads exactly like `@onCreate(SomeEvent)`) **or** a factory (`EntityErrorEventFactory = (error: unknown) => IDomainEvent`, `@onError((error) => ...)`, for an event that folds the caught error into its own payload — `Entity.raiseEvent` overwrites `occurredAt`/`aggregateId` on the way into the buffer regardless of what either form builds, so the factory is free to spend its constructor arguments entirely on the event's own payload). The two forms are told apart at runtime by `isBareEventClass` (internal), which — since both a class reference and a factory are `typeof === "function"`, unlike `raiseEvent`'s own object-vs-function dual-mode — reads the own property descriptor of `prototype` instead: an ES2015 `class`'s is spec-mandated non-writable, an ordinary `function`'s is writable, an arrow function has none at all. A detected bare class is normalized through **`fromClass`, a new public helper** that wraps it into the factory shape, ignoring the error and building a fresh instance on every call — also exported on its own for when that factory value is needed detached from the decorator call. `onError` does not share `methodHandleDecorator` with `beforeHandle`/`afterHandle` — genuinely different control flow (a bracket that can catch and build from call-time data, not a bracket around one fixed raise) — and composes with them the same bracket-nesting way any two method decorators do. A different `onError` from the one already on `eventedRegistry` (`application/evented-registry`, which isolates a throwing event *reaction* by swallowing it): same name, different layer, this one wraps an `Entity` business method and never swallows. New public types/helpers: `EntityErrorEventFactory` (under `@roastery/beans/domain/entity/decorators/types`) and `fromClass` (under `@roastery/beans/domain/entity/decorators`)
- **`collectResult(result, ...rest)`, a new public helper of `@roastery/beans/application/command/helpers`.** Collapses the two-line pattern every `Command.execute()` otherwise repeats — `{ result: entity, events: collectDomainEvents(entity) }` — into one call: `result` is both the value returned as `CommandResult.result` and the primary aggregate `collectDomainEvents` drains (deep); any further aggregates touched during `execute()` but not themselves the result can still be passed along, exactly as `collectDomainEvents` itself accepts variadic. Typed structurally, like `collectDomainEvents` (`Result extends { pullDomainEvents(...): readonly IDomainEvent[] }`), rather than against the concrete `Entity` class — a concrete `Entity<Shape>` is not structurally assignable to a nominal `Entity<PropertiesShapeBase>` bound (its `toJSON()`/`get()` return types are shape-dependent), the same incompatibility `EntityConstructor` already sidesteps for the lifecycle decorators' mixin base, so a nominal bound here would reject real entity subclasses instead of accepting them
- **`eventedRegistry`, a new function, and `@roastery/beans/application/evented-registry`, its pillar.** `commandRegistry`, gaining event behaviour: every event a registered command's `CommandResult` carries is automatically published through an injected `IEventEmitter`, and reactions registered via `.on(eventClass, handlerClass)` run — `await`ed, isolated from one another and from the command call that raised the event — before that call resolves. Delegates command construction/execution entirely to a real `commandRegistry(spec).withDependencies(dependencies)` underneath (reuse, not reimplementation), building a second, parallel `commands` bag shared by both `.get()` and every reaction's `deps.commands` — so a reaction that dispatches a sibling command runs through the exact same decorated runner, and whatever that command in turn raises is itself auto-published and auto-reacted-to, letting reactions compose. Matching a raised event against a registered `eventClass` is by `name`, never `instanceof`: `Entity.raiseEvent` spreads a built event into a fresh plain object before buffering it, so `nameOf` (internal) resolves `eventClass`'s `name` once, at `.on()` time, off an `Object.create(eventClass.prototype)` probe — the same construction-free pattern `Entity.fromJSON` already uses to read a blueprint — which is also why a handler can target an event whose constructor needs more than `aggregateId` (`OrderConfirmed(aggregateId, total)`), unlike `Entity.raiseEvent`'s own bare-class overload. A reaction is a class implementing `IEventHandler<Event, Deps>` (one method, `handle`) rather than a plain function — deliberately an interface, not an abstract base like `Command`, since a reaction has no blueprint to validate and therefore nothing to centralize. `deps.commands` is gated at compile time by a new `RegistrableEventHandlerClass`, mirroring `RegistrableKeys`/`AugmentedDependencies`/`SiblingCommands`: a handler class is only accepted by `.on()` if its declared `Deps` is structurally satisfied by what the registry actually has available, one hop deep, same limitation `Command`'s own sibling composition already documents. A throwing reaction is isolated — visible only through the optional `onError` hook, or, absent that (or if it itself throws), by re-throwing inside a microtask, never rejecting the `CommandResult` of the command that raised the event nor stopping sibling reactions. A reaction chain that cycles back to a command key or event name already on its own call chain — a reaction whose triggered command raises the same event again, directly or through further reactions — throws `LoopDetectedException` (HTTP 508) instead of recursing until the call stack gives out, the same runtime guard `commandRegistry`'s own sibling composition now has. For a cycle closing on an *event* specifically, that failure is isolated exactly like any other reaction error (routed through `onError`/`defaultOnError`) rather than thrown, still never rejecting the `CommandResult` of the command that raised the event. New public types: `IEventedRegistry`, `IEventHandler`, `IEventEmitter`, `EventedRegistryBuilder`, `EventedRegistryOptions`, `EventReactionErrorContext`, `EventReactionErrorHandler` — all under `@roastery/beans/application/evented-registry/types`
- **`defineEventHandler(handle, name?)`**, a new factory building an `IEventHandler` **class** from just its `handle` function — the same `(args) => class` idiom `defineDomainEvent`/`defineValueObject` already use, applied to the one-method class a reaction otherwise requires. The generated class's `handle` delegates straight to the given function, forwarding `event`/`deps` unchanged and propagating a rejection exactly as a hand-written class would — `eventedRegistry`'s own isolation (`onError`, or its microtask re-throw fallback) treats a generated handler exactly like one written by hand, and the generated class is directly usable with `.on(eventClass, generatedHandlerClass)`, gated by the same `RegistrableEventHandlerClass` compile-time check. `name` is optional and purely cosmetic — unlike `defineDomainEvent`'s own `name`, nothing here reads it at runtime (matching stays keyed off the *event* class's name); it only stamps the generated class's `.name` for readability in stack traces and tooling, the same `if (name) Object.defineProperty(...)` pattern `defineValueObject` already uses. Like the other class-returning factories, must be called at module scope, once: each call mints a fresh class, so two calls with the same `handle` are unrelated for `instanceof`. New public type: `EventHandlerClassOf<Event, Deps>`, under `@roastery/beans/application/evented-registry/types` — annotates the factory's return for the same TS4060 reason `DomainEventClassOf`/`ValueObjectClassOf` do
- **`Entity.pullDomainEvents({ deep: true })`**, draining the whole aggregate — this entity's buffer first, then each nested entity's, recursively, in blueprint order. The no-argument form is unchanged and still shallow. The motivating case is a nested entity carrying lifecycle decorators: `onCreate` fires every time the parent is constructed (building the parent builds the child), and a shallow pull from the root left those events in a buffer nobody ever read. `collectDomainEvents` now always pulls deep, since not losing events before they reach a `CommandResult` is the whole reason it exists; its structural parameter type declares the option as optional, so a hand-rolled aggregate whose `pullDomainEvents()` takes no argument still satisfies it
- **`Command`, a new application-layer base class, and `@roastery/beans/application`, its pillar.** Built the same way an `Entity` is — a blueprint of `ValueObject` classes, resolved through explicit value → rule `default` → rule `derive`, `blueprint(shape).with(rules)` reused unchanged — but with no identity and no mutation: no `id`/`createdAt`/`updatedAt`, no `set`/`setMany`. A `Command` is built once (validating synchronously, same as `Entity`) and then `execute(deps): Promise<CommandResult<Result>>`d, the one abstract method alongside `defineCommand()`, where all I/O and side effects belong. `CommandResult<Result>` is `{ result, events }` — `events` is always an array (mirroring `Entity.pullDomainEvents()`), and `Command` never publishes it itself, only surfaces it for the caller to decide what to do with. `defineCommand` follows the same **prototype-method, never a class field** rule as `defineEntity`/`defineMeta`/`defineName`, guarded with the same `InvalidEntityDefinitionException`. The blueprint is **value-object-only** (never a nested `Entity` or `Command`), so unlike `Entity` there is no cycle to guard against, and the construction machinery (`buildContext`, `modelFor`, `installAccessors`) lives as ordinary internal helpers under `application/command/helpers/` rather than being forced inline to dodge a circular import. `demo()` and `fromJSON()` work exactly like their `Entity` counterparts (same `Demo` sentinel, same strict whole-payload validation rejecting missing **and** extra keys). New public types: `CommandDefinition`, `CommandResult`, `CommandAccessorsOf`, `RawCommandContextOf`, `ICommand`, `SerializedCommand`, `CommandPropertiesShapeBase` — all under `@roastery/beans/application/command/types`
- **`collectDomainEvents(...aggregates)`**, the one public helper of `@roastery/beans/application/command/helpers`. Drains one or more `{ pullDomainEvents(): readonly IDomainEvent[] }`-shaped buffers and concatenates them in call order, typed structurally rather than against the concrete `Entity` class. The intended glue between `Entity.raiseEvent` (only the aggregate root may call it, from its own business methods) and a `Command`'s `CommandResult.events`: `execute()` calls a method on the entity it orchestrates, persists it, then hands `collectDomainEvents(entity)` back in its result
- **`Command` is reachable from the root barrel** (`import { Command } from "@roastery/beans"`), alongside `Entity`, `ValueObject`, `blueprint` and `DomainEvent`
- **`Command`'s own input-validation failures throw application-layer exceptions, not domain-layer ones.** A property that fails validation during construction throws `UnprocessableContentException` (422, from `@roastery/terroir/exceptions/application`) instead of the `InvalidPropertyException` a `ValueObject` normally throws — the original is preserved as `error.cause`. `fromJSON` rejecting a payload shaped wrong (missing/extra keys) throws `BadRequestException` (400) the same way, replacing what would otherwise be `InvalidDomainDataException`. Both fix `[Layer]` to `"application"`, so error-handling middleware can tell a command's own input validation apart from a deeper domain invariant failure. Definition-time mistakes (`defineCommand` declared as a class field, a colliding blueprint key, `get()`'s unknown-key guard) are unaffected — they stay the same `domain`-layer exceptions `Entity`/`ValueObject` already use, since they're not about request input at all
- **`entityOf(properties, source)` and `commandOf<Shape, Deps, Result>(properties, source)`**, factories returning a base class already bound to a blueprint. A subclass then declares only its own behaviour: `defineEntity`/`defineCommand`, the `interface X extends AccessorsOf<…> {}` declaration merge, and the `biome-ignore` that merge requires all go away, and the blueprint accessors come out **typed without the merge** — which matters, because forgetting that one line is the package's only silent failure mode (the getters still work, they just disappear from the type system). Both factories accept the rest of the definition as an optional third argument (currently `sensitive`). The class form is untouched and still correct — reach for it when a subclass computes its definition rather than stating it. Internally each descends from a new concrete base (`BoundEntity`, `BoundCommand`, neither exported from a barrel) that implements the `defineX` from a static on the generated class: naming the abstract `Entity`/`Command` in the returned type made every `class X extends entityOf(…) {}` fail with **TS2515**, since a type literal cannot say a member is already implemented. Keeping a real class type in the intersection is also what lets a subclass go on reaching `raiseEvent`, `[Storage]` and `[Events]`. New public types: `EntityClassOf` and `CommandClassOf`
- **Sensitive values are kept out of logs, declaratively and configurably.** `IValueObjectMetadata` gained `sensitive?: boolean` — a flag that travels with the class, so a `PasswordVO` (which now carries it) is secret in every blueprint that uses it — plus `redactWith?`, that class's own replacement. `defineEntity`/`defineCommand` gained `sensitive?: readonly Key[]` for the case the type alone does not settle, e.g. a `StringVO` holding an API token. Where the replacement lands is deliberately asymmetric: **`Command.toJSON()` redacts** (a command is never persisted, so nothing round-trips through it — while `toJSON` is exactly what a structured logger reaches via `JSON.stringify`), while **`Entity.toJSON()` stays lossless**, since it is the persistence contract and has to close the loop with `fromJSON`. Entities gained **`toSafeJSON()`** for the redacted view, recursing so each nested entity applies its own keys; `toString()` and Node's inspect hook redact on both bases. What the replacement *is* comes from `configureRedaction({ placeholder })` (exported from the package root), overridable per class by `redactWith`; either may be a ready value or a `(value, context)` function — receiving the real value is what makes partial masking (`a***@b.dev`) possible rather than only erasing. Config lives in module state rather than a `globalThis` key: typed, resettable between tests, and unclobberable by an unrelated package. New public exports at the root: `configureRedaction`, `redactionConfig`, and the types `IRedactionConfig`, `RedactionPlaceholder`, `RedactionPlaceholderFn`. `IEntity` grew `toSafeJSON()`
- **`blueprint(shape).done()`**, closing a rule-less blueprint. It returns the shape *as given* — same object reference, no `Rules` slot attached, since `rulesOf` already reads a missing slot as an empty map — so it is indistinguishable from the plain object literal that has always worked. It exists to replace `.with({})`, whose empty rule map read like one somebody forgot to fill in, and to let every blueprint in a codebase open and close the same way
- **`bun run example`**, running `examples/user-flow.ts` — the end-to-end dogfooding script that used to sit at the repository root as `testing.ts`. It stays inside the project's `tsconfig`, so it is type-checked with everything else (which is how a stale call site got caught rather than shipped)
- **`src/shared/helpers/`, one copy of what both pillars use verbatim.** `installAccessors`, `applyRuleDefaults` and `rulesOf` were duplicated per pillar; all three were byte-identical in behaviour, so the copies only guaranteed that a fix to one would silently miss the other. `installAccessors` had been documented as differing "in the nested-entity branch of the getter" — it never did: the getter is `return this.get(key)` in both, and the nested-entity branch lives in `Entity.get`. Its only real difference, the pillar name quoted in `PropertyNameCollisionException`, is now a `label` parameter. The directory deliberately carries **no barrel**: `exports` maps `./*` onto `dist/*/index.d.ts`, so any `index.ts` would publish it as a subpath. `readDefinition` stays duplicated per pillar, since its entire content is the pillar-specific method name it probes and the message explaining the class-field trap. No public API changed — all six files were internal
- **A spec pinning the `application/collections` alias to its domain original.** The six mirrored barrels are kept in sync by hand, with nothing enforcing it. `application/collections/collections-alias.spec.ts` now checks both halves: name parity read from the barrels' *source* (so the type-only `custom/types` subpath is covered, where a runtime `Object.keys` comparison would pass vacuously on two empty namespaces), and reference identity at runtime for the five value-carrying subpaths — catching a barrel that *redeclares* a class instead of re-exporting it, which would keep every name lined up while quietly breaking `instanceof` and handing `SchemaManager` a second cache key
- **`@roastery/beans/application/collections/*`**, a thin alias mirroring every `@roastery/beans/domain/collections/*` subpath (`schemas`, `value-objects`, and the `optional`/`nullable`/`custom` variants) — the exact same classes, re-exported so a `Command` blueprint never has to import from the domain layer's subpaths directly
- **`Entity.destroy()`/`Entity.isDestroyed`.** A lightweight lifecycle marker, not a hard guard: `destroy()` flips a private `#destroyed` field and releases the transient `[Storage]` (via the new `EntityStorage.clear()`), idempotently — a second call is a no-op — but `get`/`set`/`toJSON`/etc. keep working afterwards. There is no way to force garbage collection from inside the entity itself, so "removed from memory" means the transient cache is released and the fact is recorded, not that the instance becomes unusable
- **`@roastery/beans/domain/entity/decorators`, three new standard (TC39) class decorators**: `onCreate`, `onUpdate`, `onDelete` — each raises a declared, payload-less `DomainEvent` at one point of an entity's lifecycle, so a subclass stops calling `this.raiseEvent(...)` by hand at that point. `onCreate` fires on a fresh construction (no `id`/`createdAt`, including `.demo()`), decided by the same `extractIdentity` rule the base constructor itself already applies; a hydration raises nothing. `onUpdate` fires when `set`/`setMany` actually changes something (read off the `boolean` those now return, not off `updatedAt`). `onDelete` fires the first time `destroy()` is called, never on a repeated call. Stackable — a class may carry all three, each touching only its own concern (constructor, `setMany`, or `destroy`) and delegating the rest via `super`. **There is deliberately no `onRead`/`onHydrate`**: rebuilding an entity from storage changes nothing, so it is not a domain fact, and an event raised there would ride along in every `CommandResult` — a command that merely loads an aggregate in order to delete it would surface a spurious "read" next to the real event. Audit reads in the repository, where the read actually happens. New type: `BareDomainEventClass`, under `@roastery/beans/domain/entity/decorators/types`
- **`@roastery/beans/domain/entity/decorators`, two new standard (TC39) method decorators**: `beforeHandle`, `afterHandle` — raise a declared, payload-less `DomainEvent` (the same `BareDomainEventClass` contract the three lifecycle decorators already use) immediately before or immediately after an **arbitrary `Entity` instance method** runs, rather than a fixed lifecycle point. Both share one internal helper, `methodHandleDecorator(event, runBefore)` (`domain/entity/decorators/helpers`), justified the same way `onCreate`/`onRead` once shared a helper before `onRead` was removed: two genuinely parallel consumers, differing only in which side of the wrapped call the event lands on. `afterHandle` never fires if the wrapped method throws — there is no `try`/`catch`, the exception simply propagates before the raise is reached — and neither decorator awaits a returned `Promise`. Stacking `beforeHandle` and `afterHandle` on the same method always raises before → method → after, regardless of which is written closer to the method. The wrapper keeps the original method's name (reusing `renameDecorated`) and, unlike the class decorators, needs no `abstract class`/mixin machinery at all — a method decorator receives and returns a plain function. New type: `EntityMethodDecorator`, internal to the decorators pillar (not re-exported from `.../decorators/types`)
- **`commandRegistry`, a new two-phase builder, and `@roastery/beans/application/command-registry`, its pillar.** `commandRegistry(spec).withDependencies(dependencies)` — the same two-phase shape `blueprint(shape).with(rules)` uses, for the same reason: a literal can't reference its own `typeof`, so `spec` is fixed by the first call before `dependencies` is checked against it in the second. `spec` is a `Record<string, AnyCommandClass>`; `.get(key)` resolves to a **ready-to-run bound function** — `await registry.get("createUser")(payload)` constructs the command with `payload` and calls `execute(dependencies)` on it, resolving to the same `CommandResult<Result>` `execute()` itself returns. The "may only register a command whose dependencies are present" rule is **compile-time only**: a command key whose declared `Deps` isn't structurally satisfied by the provided dependency record is a type error on `.get()`, not a runtime check — `Command` gains no new member or symbol for this. A command declaring `Deps = void` is always registrable, regardless of the record. An unknown key at runtime throws `InvalidPropertyException`. New public types: `AnyCommandClass`, `CommandRegistryBuilder`, `CommandRegistrySpecBase`, `CommandRunner`, `ICommandRegistry` — all under `@roastery/beans/application/command-registry/types`
- **`commandRegistry` composes commands with each other — "sibling commands."** Every registered command's `execute()` now additionally receives a `commands` bag under `Deps` — one already-bound `CommandRunner` per sibling that is **directly** satisfiable from the raw `Dependencies` record alone (`DirectlyRegistrableKeys`), letting a command reuse an already-registered use case (`deps.commands.login(...)`) instead of duplicating its logic. Restricted to **one hop**: a sibling that itself needs `commands` isn't provably safe at compile time and is excluded from the bag's *type*, even though the runtime composition has no such depth limit — the bag is reachable via `.get()` externally and via `commands.key` from inside another command alike; only what `.get()`'s type can prove is capped at one hop. That unlimited runtime depth now has its own backstop: a chain that calls back into a key already on its own call chain throws `LoopDetectedException` (HTTP 508, from `@roastery/terroir/exceptions/application`) instead of recursing until the stack overflows — tracked via an immutable `chain` threaded fresh through each nested `execute()`'s own `commands` bag (rebuilt per call, not one flat shared object, so two unrelated concurrent calls to the same key are never mistaken for a cycle). New public types: `SiblingCommands`, `AugmentedDependencies`, `DirectlyRegistrableKeys` — all under `@roastery/beans/application/command-registry/types`. Additive: `commands` only appears in a command's `Deps` when that command's own type declares it, so no existing `Command`/`commandRegistry` usage is affected
- **`commandRegistry` is reachable from `@roastery/beans/application`**, the application layer's own root barrel, alongside `Command` — previously only importable from its own subpath, `@roastery/beans/application/command-registry`. The subpath import still works unchanged; this only adds the shorter path, matching how `Command` itself is reachable from both the package root and this barrel
- **`EntityHas<EntityType, ExpectedShape>`**, a new compile-time check for whether an entity's blueprint carries a given set of fields, each backed by — or aliased from, via a domain-vocabulary subclass such as `class PostAuthorId extends UuidVO {}` — a specific `ValueObject` class. Resolves to the boolean literal `true`/`false`, meant to compose with a conditional type (e.g. gating a generated repository method on the fields it needs: `EntityHas<typeof Post, { authorId: typeof UuidVO }> extends true ? { findByAuthorId(id: string): ... } : {}`). **`entityHas(entityClass, expectedShape)`**, its runtime counterpart under `@roastery/beans/domain/entity/helpers`, performs the same check against a class actually available at runtime and returns a plain `boolean` — for call sites where the entity class or expected shape isn't a compile-time literal. Both compare the full VO **class** (via its prototype), not just the runtime value it wraps — the only way to tell apart two VOs that happen to share a value type but validate differently, such as `SlugVO` and `StringVO`, both backed by `string`. New public types: `EntityHas`, `EntityHasShapeBase`, under `@roastery/beans/domain/entity/types`
- **`defineDomainEvent(name)`**, a new factory building a payload-less `DomainEvent` **class** from just its name — the same "factory returns a class" idiom `domain/collections/value-objects/custom` already uses for `ValueObject` (`defineValueObject`, `customStringVO`, etc.), applied to the one-`defineName()`-method subclass that a payload-less event otherwise requires. The generated class's constructor is exactly `(aggregateId: string)`, so it's a drop-in for `Entity.raiseEvent`'s bare-class form (`this.raiseEvent(UserCreated)`, no `new`) and for the lifecycle/method decorators (`@onCreate(UserCreated)`), which already only accept that shape. An event with payload fields of its own still needs a hand-written subclass — a constructor with extra required parameters isn't something a `(name: string) => Class` factory can produce. Like the custom value-object factories, must be called at module scope, once: each call mints a fresh class, so two calls with the same name are unrelated for `instanceof`. New public type: `DomainEventClassOf`, under `@roastery/beans/domain/domain-event/types` — annotates the factory's return for the same TS4060 reason `ValueObjectClassOf` does (the class is declared inside the function body, so an inferred return type fails the declaration build), but takes no type parameters since `DomainEvent` itself is not generic

### Changed

- **BREAKING: `src/` split into `domain/` and `application/`, and every existing subpath moved under `domain/`.** `@roastery/beans/entity` → `@roastery/beans/domain/entity` (and all of its `/helpers`, `/types`), `@roastery/beans/value-object` → `@roastery/beans/domain/value-object`, `@roastery/beans/domain-event` → `@roastery/beans/domain/domain-event`, `@roastery/beans/collections/*` → `@roastery/beans/domain/collections/*`. The root barrel (`import { ... } from "@roastery/beans"`) is **unaffected** — it still re-exports `Entity`, `ValueObject`, `blueprint` and `DomainEvent` (now alongside `Command`) — only the deeper subpaths moved. No behavior change to any existing class or helper, only where it's imported from

### Fixed

- **`fromJSON` no longer rejects a payload that simply omitted an `optionalVO`-backed key.** `modelFor` (both pillars) put every blueprint key in the schema's `required` list, including the ones whose value-object accepts `undefined`. `toJSON()` emits such a key as present-with-`undefined`, which `JSON.stringify` then drops entirely — so a payload that made a real round-trip came back missing it, and `Entity.fromJSON` threw `InvalidDomainDataException` while `Command.fromJSON` threw `BadRequestException`. The second was the worse of the two: `Command.fromJSON` is the documented entry point for an untrusted HTTP body, so a client omitting an optional field got a 400. Those properties are now emitted through `t.Optional`, decided per-property by asking the schema itself whether it accepts `undefined` (structural, so a hand-rolled schema behaves like an `optionalVO` one). `SerializedValuesOf` and `SerializedCommand` relax the same keys at the type level, so the type and the runtime validation agree. **Nullable keys are deliberately unaffected** — `null` survives `JSON.stringify`, so a `nullableVO`-backed key stays required, preserving the `optional` (may not have been provided) vs. `nullable` (provided, explicitly empty) split
- **`onUpdate` no longer swallows a second mutation landing in the same millisecond.** The decorator inferred "something changed" by comparing `updatedAt` before and after the call, but that stamp is an ISO string with millisecond resolution — two genuinely distinct mutations in the same tick produced the same timestamp, so only the first raised an event. `set`/`setMany` now **return a `boolean`** (the change flag they already computed to decide the `updatedAt` stamp) and the decorator reads that instead. `IEntity` reflects the new return type; callers ignoring it are unaffected
- **A nested entity's payload is now relaxed at every depth, not just the first.** `NestedEntityInput` derived its shape from `Omit<ReturnType<toJSON>, keyof IRawEntity>` — the serialized form, which carries identity at every level — and stripped `keyof IRawEntity` only at the outermost one. A *grandchild* therefore still demanded its `id`/`createdAt` **and** the keys its own blueprint rules cover, so a three-level aggregate (`new Blog({ post: { title, author: { name } } })`), or `set` on a nested entity that itself holds an entity, was a compile error even though the runtime accepted it and generated the identity correctly. This violated the invariant the type exists to uphold — that nesting must not change what the domain considers a complete payload — which held at one level and broke at two. It is now `ConstructionValuesOf<Shape>`, the same type the top level uses, which reaches nested entities back through `InputValueOf` and so recurses for free. **Type-level only**: no runtime behaviour changes, and the guards are unaffected — a grandchild's half-given identity, unknown key, or genuinely missing required key are all still rejected
- **A decorated class keeps its own `name`.** Every lifecycle decorator returns `class Decorated extends target`, so `User.name` read `"Decorated"` for every decorated entity. Nothing inside `beans` reads `Class.name` — the blueprint machinery is entirely structural — but consumers' stack traces, log lines and DI containers do, and four different entities all reporting as `Decorated` made those unreadable. The four decorators now share `renameDecorated` (`domain/entity/decorators/helpers`), which copies the original name onto the wrapper

## [0.3.0] - 2026-08-17

### Added

- **`Entity.raiseEvent`/`Entity.pullDomainEvents`.** Domain events, buffered per instance behind the new `[Events]` slot and drained explicitly — nothing dispatches them, `beans` stops at the buffer, whatever happens with the drained array is the consuming application's call. `raiseEvent` (`protected`) takes only `name` plus whatever payload the caller's event carries; it stamps `occurredAt` and `aggregateId` itself, from `DateTimeVO.now` and the entity's own `id`, so every event carries at least its raising entity's identity and no subclass can override either field — `beans` is not event-sourced, so there is no replay path that would need to. Never fires on its own: `set`/`setMany` do not raise events, only an explicit call from a subclass's own business method does. Only the aggregate root should call it — an event raised inside a nested entity stays in that nested entity's own buffer, since `pullDomainEvents` does not recurse through `[Context]` the way `toJSON` does. `pullDomainEvents` (`public`) returns everything buffered since the last pull, oldest first, and empties the buffer. Starts empty on all three construction paths (`new`, `fromJSON`, `demo`), same guarantee as `[Storage]`, and never reaches `toJSON()` or the schema. `IEntity` grew a matching `pullDomainEvents()` member. `raiseEvent` also accepts a **bare class reference** in place of a built event — `this.raiseEvent(OrderConfirmed)` instead of `this.raiseEvent(new OrderConfirmed(this.id))` — for any `DomainEvent` subclass whose constructor takes only `aggregateId`; the base instantiates it itself, passing `this.id`. A subclass whose constructor needs more than `aggregateId` isn't assignable to that shape, so TypeScript routes it to the already-built branch and rejects the bare form at compile time — the constructor signature is the guard, no runtime check needed
- **`@roastery/beans/domain-event`, a new pillar.** `IDomainEvent` (`.../domain-event/types`) is the `{ name, occurredAt, aggregateId }` contract `Entity.raiseEvent` builds, and `DomainEvent` (`.../domain-event`) is an optional abstract base for writing concrete event classes against it: a subclass declares only `defineName()` — the event's stable, dot-namespaced name — and passes `aggregateId` up through `super()`; `occurredAt` is stamped by the base itself, the same `DateTimeVO.now` stamp `Entity.raiseEvent` uses. Sugar over `IDomainEvent`, not a replacement for it — `raiseEvent` already accepts a plain `{ name, ...payload }` object and stamps `occurredAt`/`aggregateId` on its own regardless of what it's given, so `DomainEvent` only pays off for events with their own payload fields, where a class reads better than repeating the object literal at every call site, and lets an event be constructed and inspected on its own, without an `Entity` in the loop. `defineName` follows the same **prototype-method, never a class field** rule as `defineMeta`/`defineEntity`, guarded at runtime with the same `InvalidEntityDefinitionException`
- Bumped the `@roastery/terroir` dependency to **0.2.1**, which now ships the `Events` slot symbol (`@roastery/terroir/symbols`) alongside the other seven — the same move `Rules` made in terroir 0.2.0 (see `[0.2.0]`, below). `Entity`'s domain-event buffer keys off it directly; this package ships no local symbol file for it

### Changed

- **`blueprint` and `DomainEvent` are now also reachable from the root barrel** (`import { blueprint, DomainEvent, Entity, ValueObject } from "@roastery/beans"`), and `blueprint` from `@roastery/beans/entity` alongside `Entity` too — both were already public (`@roastery/beans/entity/helpers` and `@roastery/beans/domain-event` respectively, still valid), this only widens where they're reachable from, since a blueprint with rules is typically declared right next to its `Entity` subclass. No behavior change

## [0.2.0] - 2026-08-15

### Added

- **`Entity`, rebuilt.** The blueprint-driven base (formerly `BetterEntity`) is now _the_ `Entity`, exported from `@roastery/beans` and `@roastery/beans/entity`. Subclasses declare a blueprint (`{ field: SomeVO }`) and a `defineEntity()` method; the base derives validated construction (with optional all-or-nothing identity), `toJSON`/`fromJSON` (the latter a strict static that validates the whole payload first), atomic `set`/`setMany` with a single automatic `updatedAt` stamp, read-only accessors typed via `AccessorsOf`, an aggregate TypeBox schema memoized per class, `demo()` fixtures, nested-entity aggregates with cycle detection, and the `[Storage]` transient store
- **`ValueObject`, rebuilt.** The self-validating base (formerly at `value-object/new.ts`) is now _the_ `ValueObject`: subclasses declare only `defineMeta()` (`{ default, schema }`) and optionally override `transform()`; validation runs in the constructor, so no instance exists unvalidated. `demo(context)` builds from the declared default, which may be a thunk for expensive values
- **Blueprint rules.** `blueprint(shape).with(rules)` (from `@roastery/beans/entity/helpers`) declares a blueprint that carries the domain's own rules: `{ default }` for a fallback belonging to the _entity_ rather than to the value-object, and `{ derive }` for a property computed from its siblings. Ruled keys become optional in the constructor payload, so the domain's defaults and derivations stop needing a hand-written constructor — which is also what keeps `fromJSON`/`demo()` intact, since a custom constructor is exactly what breaks them. Precedence is explicit value > `default` > `derive`; derivations run in blueprint order over already-normalised siblings; rules apply in `demo()` (fixtures stay coherent) and to a **nested** entity's payload, but never re-fire on `set`/`setMany`; the derived schema and `fromJSON`'s strictness are untouched. Declaring both `default` and `derive`, or naming a property outside the blueprint, is a compile error and an `InvalidEntityDefinitionException` at runtime. New public types: `PropertyRule`, `RulesOf`, `RuledBlueprint`
- The `Rules` slot symbol, declared **temporarily** in this package (`src/entity/rules.symbol.ts`) instead of `@roastery/terroir/symbols`, where it belongs. It is the single exception to the repository's "never declare a slot symbol locally" rule and exists to be deleted — `docs/terroir-rules-slot.md` tracks the move to terroir 0.2.0
- **Custom value-object factories.** `@roastery/beans/collections/value-objects/custom` ships functions that return a `ValueObject` **class** rather than an instance, so a blueprint can declare a constrained property inline instead of paying a schema plus a subclass for every domain rule: `customStringVO`, `customNumberVO`, `customArrayVO` (item schema as its first argument), `customObjectVO` (declared shape, `additionalProperties: false`), `customRecordVO` (free-form bag), and the core `defineValueObject` they all lower into — reach for that one when the schema already exists. All accept the same hooks: `default` (value or thunk), `name` (stamped onto the class), `transform(value)`, and `validate(value, context)` — a **predicate** running after the schema has accepted the transformed value, raising `InvalidPropertyException` with the owning entity's `name`/`source` when it returns `false`. Ready defaults are validated **inside the factory call**, so a placeholder the options reject (`customStringVO({ options: { minLength: 8 } })`) raises `InvalidEntityDefinitionException` at import time rather than at the first `demo()`; thunk defaults stay lazy and are validated by the base in demo mode. `customObjectVO` requires an explicit `default`, since no placeholder can satisfy an arbitrary set of required properties. Each call mints a fresh schema and a fresh class, so factories belong at module scope: calling one inside `defineEntity()`/`defineMeta()` defeats the compiled-validator and aggregate-model caches, both keyed by object identity. New public types under `@roastery/beans/collections/value-objects/custom/types`: `ValueObjectClassOf`, `IDefineValueObjectArgs`, `ICustomValueObjectArgs`, `IValueObjectHooks`
- `@roastery/beans/value-object/helpers` subpath — `metaOf`, reading a VO class's `{ default, schema }` without constructing an instance
- `@roastery/beans/entity/types` grew the blueprint type surface: `IEntity` (the rebuilt contract), `AccessorsOf`, `EntityDefinition`, `PropertiesShapeBase`, `RawContextOf`, `SerializedEntity` (plus the supporting aliases as internal one-type-per-file modules)
- Four new collection value-objects on the rebuilt base: `EmailVO`, `NumberVO`, `PasswordVO`, `SimpleUrlVO` — completing one VO per schema
- The v1 sugar statics, recreated on the rebuilt VOs: `BooleanVO.truthy/falsy/from`, `DateTimeVO.now`, `UuidVO.generate`

### Changed

- **BREAKING** — migrated to `@roastery/terroir` **0.2.0**, which removed the `Schema<T>` wrapper class. A TypeBox schema is now the runtime value itself: `Schema.make(XDTO)` is gone, `schema.match(v)` became `SchemaManager.match(XSchema, v)`, `schema.toString()` became `SchemaManager.serialize(XSchema)`, and `Schema<T>` as a type annotation collapsed to `T`. `Entity`'s per-blueprint cache now memoizes only the derived `t.TObject` — the compiled validator is cached by `SchemaManager` against the schema's object identity, so keeping the model stable is what keeps validation to one compilation per blueprint
- **BREAKING** — the slot symbols (`Context`, `Demo`, `Meta`, `Properties`, `Source`, `Storage`) now come from `@roastery/terroir/symbols`; `@roastery/beans/actions` and the `src/actions/` directory behind it are gone. Symbol equality is by reference, so hosting them in one package is what lets a consumer read the same slot `beans` wrote — a duplicate declaration failed silently, returning `undefined` and quietly breaking the type-level matches (`Instance extends { [Properties]: infer Shape }`)
- **BREAKING** — the whole collection VO catalog (`BooleanVO`, `DateTimeVO`, `DefinedStringVO`, `SlugVO`, `StringArrayVO`, `UrlVO`, `UuidArrayVO`, `UuidVO`) moved to the rebuilt base: construction is `new XVO(value, context)` instead of `XVO.make(value, info)`, and demo/default construction is `XVO.demo(context)`
- **BREAKING** — `defineMeta()` returns `{ default, schema }`; the metadata field was renamed from `model` to `schema`, matching what it now holds
- **BREAKING** — the five domain failures that used to collapse into `OperationFailedException`/`InvalidPropertyException` now raise the dedicated classes terroir 0.2.0 added for them, so consumers can discriminate on the type instead of a message substring: a blueprint cycle raises `CyclicEntityDefinitionException`; a `defineEntity`/`defineMeta` declared as a class field raises `InvalidEntityDefinitionException`; a blueprint key colliding with an existing member raises `PropertyNameCollisionException` (carrying the key in its `property` slot); a half-given identity raises `IncompleteIdentityException`; and writing to `id`/`createdAt`/`updatedAt` through `set`/`setMany` raises `ImmutablePropertyException` — previously indistinguishable from an unknown key
- `Entity.setMany` stamps `updatedAt` through `DateTimeVO.now` (same behaviour, named for what it does)
- All source TSDoc and runtime error messages are now in English

### Removed

- **BREAKING** — `Mapper` (`@roastery/beans` root and `@roastery/beans/mapper`), `ParseEntityToDTOService` (`@roastery/beans/entity/services`) and `EntityUpdater` (`@roastery/beans/entity`). Their capabilities live on the rebuilt `Entity` as `toJSON`/`fromJSON`/`set`/`setMany`

- **BREAKING** — the v1 `Entity` base (schema-parameterised, `super(data, source)`, hand-written getters) and the v1 `ValueObject` base (`protected schema` + `static make` + deferred `validate()`), replaced by the rebuilt pillars above
- **BREAKING** — `@roastery/beans/entity/symbols` (`EntitySource`, `EntitySchema`, `EntityContext`, `EntityStorage` symbols; superseded by `@roastery/terroir/symbols`), `@roastery/beans/entity/decorators` (`@AutoUpdate` — the stamp is automatic now), and `@roastery/beans/entity/schemas` (the runtime `EntitySchema` instance, which had no consumers)
- **BREAKING** — the `@roastery/beans/collections/dtos` subpath and the 12 `*.dto.ts` files behind it. Without the `Schema` wrapper, `XDTO` and `XSchema` were the same value under two names; the surviving name is `XSchema` (`@roastery/beans/collections/schemas`), so `collections/` ships pairs rather than triplets
- **BREAKING** — `IdObjectDTO`/`IdObjectSchema` and `SlugObjectDTO`/`SlugObjectSchema`, unused query-parameter shapes with no matching VO
- **BREAKING** — the `@roastery/beans/entity/dtos` subpath and `EntityDTO`, the TypeBox schema/type pair for `id`/`createdAt`/`updatedAt`.
