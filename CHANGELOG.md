and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **`arrayOf`, `optionalOf` and `nullableOf` — multiplicity wrappers over a blueprint class, and `@roastery/beans/domain/wrapper`, their pillar.** Each takes one blueprint class — a `ValueObject`, an `Entity` or a `DomainRecord` — and returns another blueprint class holding **many** of it, **optionally one**, or **one-or-`null`**. They exist so multiplicity stops leaking into the ubiquitous language: until now "a post has many tags" had to be spelled as a `TagListVO` or a `PostTags` record, names that are not domain concepts but variations on one. The catalog already solved this for *schemas* (`customArrayVO`, `optionalVO`, `nullableVO`), which is a different thing and stays: those wrap a schema and therefore only ever reach a value-object, while these wrap a **class**, inheriting its `transform`, `validate`, `sensitive` and its whole blueprint. Admitted in all three pillars' blueprints, `Command` included. Also re-exported from `@roastery/beans/way` and aliased at `@roastery/beans/application/wrapper/helpers`
- **A wrapped key relaxes item by item, and reads back unwrapped.** `new Post({ tags: [{ name: "Alan Reis" }] })` means exactly what `new PostTag({ name: "Alan Reis" })` means — the item's own `derive`/`default` rules run, its identity stays optional-all-or-nothing, its `optionalVO` keys stay omittable — because `InputValueOf` is the same type either way, at every depth. `post.tags` is the `readonly PostTag[]` itself, not a collection object: a wrapper states a multiplicity, it does not become a domain concept. The cost is stated rather than hidden — there is no `.add()`, and appending replaces the whole list through `set`, passing the existing items back through `toJSON()` to preserve their `id`s
- **`pullDomainEvents({ deep: true })` walks into a wrapper's contents.** An entity inside an `arrayOf` raises into its own buffer, so without the forward its events would be stranded — the one failure in the feature that would have been entirely silent. The shallow form still returns only the owner's own events
- **New types**: `AnyWrapper`, `AnyWrapperClass`, `IWrapper`, `WrapperClassOf`, `WrapperKind`, `WrappedInputOf`, `WrappedRawOf`, `WrappedReadOf` (`domain/wrapper/types`), and `WrappableClass` (`domain/entity/types`) — the three singular kinds a wrapper may wrap. New runtime discriminants `isWrapperClass`/`isWrapper` (`shared/helpers`), the only ones in the package probing a **static** rather than a prototype method, because that static is also what the type level reads

- **`SchemaVO`, `OptionalSchemaVO`, `NullableSchemaVO` and `SchemaSchema`** — the twenty-first entry in the collections catalog, and the odd one out: its value is a **JSON-serialized TypeBox schema** (the wire form `SchemaManager.serialize` produces), for the case the shape of some data is decided at runtime rather than at compile time — a CMS whose post types each declare the shape of their own payload. It stores the wire string rather than a live `TSchema` because a hydrated schema carries a non-enumerable `[Kind]` symbol that `JSON.stringify` strips, so an entity holding one would not round-trip. `SchemaVO.match(schema, value)` checks arbitrary content against a stored schema, taking either the VO or a raw wire string; `SchemaVO.from(tSchema, context)` is the producer side. Validation is two layers — `SchemaSchema`'s `json` format answers "does this parse", and `validate()` hydrates to answer "does TypeBox compile it", which no JSON Schema can express: `'{"type":"banana"}'` passes the first and fails the second

- **`DomainRecord`, a new domain-layer base class, and `@roastery/beans/domain/record`, its pillar.** An `Entity` **minus identity**: no `id`, `createdAt` or `updatedAt`, never a row, no repository port derived from it — but everything else an entity has, including mutation. It exists for the composite domain values that deserve verbs (`Money`, `Address`, `DateRange`), which until now had to be flattened into a `customObjectVO` that validates their shape and can do nothing else. `set`/`setMany` are `protected` exactly as on `Entity`, so a record changes only through the domain verbs its subclass names. Reachable from the root barrel alongside `Entity`, `ValueObject`, `blueprint` and `DomainEvent`
- **`recordOf(properties, source, extra?)`** (`@roastery/beans/domain/record/helpers`, and re-exported from `@roastery/beans/way`), `entityOf`'s twin: a base class already bound to a blueprint, so the subclass owes neither `defineRecord()` nor the `interface X extends RecordAccessorsOf<…> {}` merge
- **A blueprint key may now hold a record, in all three pillars.** `Entity`, `Command` and `DomainRecord` blueprints all accept a `DomainRecord` class, and a record's own blueprint accepts value-objects, entities and records alike. `get` returns the nested **instance** for a record-valued key, so its verbs stay reachable (`post.money.plus(10)`); `toJSON`/`toSafeJSON`/`schema`/`fromJSON` recurse through it at every depth
- **`DomainRecord` forwards a deep domain-event drain without ever raising one.** It has no `[Events]` slot and no `raiseEvent` — an event belongs to an aggregate root, and a record has no identity to report as its `aggregateId`. But because a record's blueprint may hold an entity, `pullDomainEvents({ deep: true })` walks into it, so an entity nested behind a record is never stranded. The shallow form always returns `[]`
- **`onSet()`, a per-property business-rule hook on `Entity` and `DomainRecord`.** A protected, empty-by-default method returning one handler per blueprint key, run on the raw value **just before** that property is built — on `new`, `fromJSON`, `demo()`, `set` and `setMany` alike. Where `blueprint().with()` *produces* a value (`default`/`derive`), this *checks* one: the handler returns `void` and enforces by throwing, never by rewriting (normalising stays the value-object's `transform`). It receives the value typed from the property's own class plus the same read-only raw view a `derive` rule gets — earlier siblings already normalised on construction, current values under the batch on mutation. Handlers all run before the build phase, so one that throws leaves the aggregate untouched and stamps no `updatedAt`. A key with no raw value to set fires nothing, so `demo()` fires only the derived keys. New types: `SetHandlerOf`/`SetHandlersOf` (`domain/entity/types`) and their named aliases `RecordSetHandlerOf`/`RecordSetHandlersOf` (`domain/record/types`), pinned in `record-type-parity.spec.ts`. Like `defineEntity`/`defineRecord`, `onSet` must be a prototype method and must be pure — the class-field mistake is only half detectable, so the guard throws `InvalidEntityDefinitionException` on the first mutation rather than letting the rule stay silently dead. `Command` gets no `onSet`: it never mutates
- **A registry key is reachable as a method: `registry.createUser(payload)`.** Both `commandRegistry` and `eventedRegistry` now install one bound runner per spec key alongside `.get(key)`, so the quoted string and the extra parentheses are gone from the common case. Identical value on both paths — `registry.createUser` **is** `registry.get("createUser")` — and identical guarantees: the same `RegistrableKeys` gate (a key whose `Deps` the supplied record doesn't satisfy is absent from the type), the same sibling bag, the same `LoopDetectedException` cycle guard, and, on the evented side, the same auto-publication and reactions, on the same identity `.on()` chains through. `.get(key)` is unchanged and stays the way out for a key held in a variable or one whose name is not a valid identifier. A spec key colliding with a member the registry already carries (`get`; also `on`, for `eventedRegistry`) throws `PropertyNameCollisionException` from `withDependencies`, atomically — nothing is installed. As with the gate itself, the runtime installs every spec key while the type exposes only the registrable ones: registrability has no runtime footprint to read. New types: `CommandRunnersOf` and `CommandRegistryOf` (`application/command-registry/types`), `EventedRegistryOf` (`application/evented-registry/types`)

- **A command names its sibling commands by class, and `deps.commands` types itself.** `commandOf`, `aggregateCommandOf` and `defineUseCase` take an optional fourth type argument — `Siblings`, a map of registry key to command **class** — and both `defineEventHandler` overloads take it third. The `commands` bag is derived from it through the new `WithSiblingCommands<Deps, Siblings>` type, so a use case reaching a sibling no longer writes `commands: { login: CommandRunner<typeof LoginCommand> }` into its own `Deps` by hand. Both registries already injected that bag at runtime; only the type had to catch up. Omitting the parameter leaves `Deps` byte-for-byte as before, and the compile-time gate is unchanged — a sibling reachable only *through* another sibling's `commands` is still not provably safe, and `.get()` still withholds it

### Changed

- **`AnyPropertyClass` has a fourth branch, and the four stay disjoint by construction.** A wrapper instance is structurally indistinguishable from a record one — both carry `toJSON`, `toSafeJSON`, `schema` and `pullDomainEvents`, and `unwrap` is a method a record is free to declare — so the discriminant went on the **class** side: `AnyEntityClass` and `AnyRecordClass` now declare `readonly wraps?: never`, which nothing carrying a real `wraps` can satisfy. Static of purpose: blueprint keys become *instance* accessors, so a key literally called `wraps` can never shadow it, unlike the instance-side `?: never` idiom `AnyRecord` uses
- **The blueprint conditionals probe a wrapper's two statics inline rather than testing `extends AnyWrapperClass`.** The full structural form drags `AnyWrapper`'s five members into the comparison at every key of every blueprint, and TypeScript gives up on a real aggregate with **TS2589**; that was measured, not guessed. `WrappableClass` exists for the same reason one level up: typing `wraps` as `AnyPropertyClass` makes the two types mutually recursive. Stopping the union one level short is also the type-level statement of a documented contract — **a wrapper does not wrap a wrapper**
- **Two runtime points gained a branch, and only two.** `get` unwraps (before the value-object test, since a wrapper is a container), and each pillar's `modelFor` derives the multiplicity into the schema — `t.Array` / `t.Union`, the `optional` form falling through the existing `acceptsUndefined` line so the key drops out of `required` on its own. `buildProperty`, `rawOf`, `toSafeJSON`, `setMany`'s change detection and the deep drain all needed nothing: they discriminate value-object versus not, and a wrapper is a container like any other
- **`RepositoryFilterKeysOf` excludes a wrapped key**, so `findByTags`/`findByAuthor` are compile errors: a list is not a predicate, and an optional entity is the nested-entity case with an extra state. `testing/helpers/filter-keys-of.ts` needed **no change at all** — its test has been *positive* (`isValueObjectClass`) since the record pillar landed, which is exactly what a fourth property kind was meant to prove

- **`SchemaVO` hydration is memoized by wire string** (`collections/value-objects/helpers/schema-cache.ts`). Not an optimization looking for a problem: `SchemaManager`'s compiled-validator cache is a `WeakMap` keyed by the schema *object*, and `SchemaManager.build` mints a fresh one from `JSON.parse` on every call, so every build misses it — measured here at 3.53 µs against 0.010 µs for a stable object, a factor of ~364. `isSchemaWire` also replaces `SchemaManager.isSchema` in `validate()`, which compiled and discarded (1.84 µs per construction), so constructing the VO now *warms* the cache the next `match` reads. The cache is a `Map`, not a `WeakMap` (a string is not a GC root), and therefore carries a `MAX_CACHED_SCHEMAS = 256` ceiling with a `clear()` on overflow, so a `SchemaVO` built from an untrusted body cannot grow it without bound

- **`AnyPropertyClass` has three branches, and `AnyEntity`/`AnyRecord` are disjoint by construction.** A record carries `toJSON`, `toSafeJSON`, `schema` and `pullDomainEvents` just as an entity does, so without a discriminant the two would be structurally identical and every conditional in the blueprint machinery would silently depend on the order its branches are written in. `AnyEntity` now declares `id: string` and `AnyRecord` declares the three identity fields as `?: never` — the same mutual-exclusion idiom `PropertyRule` already uses for `default`/`derive`. The runtime half is `DomainRecord` rejecting `id`/`createdAt`/`updatedAt` as blueprint keys with `PropertyNameCollisionException`
- **`CommandPropertiesShapeBase` accepts a `DomainRecord` class.** A command's input may now carry a composite value with verbs instead of a `customObjectVO`. Two consequences, both stated rather than engineered around: a record blueprint may itself hold an entity, so a command payload can reach one transitively; and a command blueprint can now close a cycle, which the record pillar's own guard catches — this pillar delegates rather than reimplementing one
- **The property discriminants are structural, not `instanceof`.** `isEntityClass` and the new `isRecordClass` live in `@/shared/helpers` and test `defineEntity`/`defineRecord` on the prototype, joining `isValueObjectClass`, which already worked this way. That is what lets each pillar classify the other's classes without importing them, and it is what made `modelFor` extractable from `entity.ts` into `entity/helpers/model-for.ts` — the two pillars' `modelFor`s now delegate to each other through class-free modules, so the cycle between them resolves at call time and never during module evaluation
- **`cycleError` moved to `@/shared/helpers` and takes a `label`,** the same shape `installAccessors` already had. Each pillar keeps its own `deriving`/`constructing` sets and its own schema memo — the memos *must* stay separate, since the entity one holds a schema carrying the identity fields. Per-pillar guards still catch a cycle that alternates pillars (`Entity A → Record R → Entity A`), because the nested call happens inside the outer guard's own `try`
- **The registrability gate is one type with a depth flag, not two near-identical types.** `RegistrableKeys<Spec, Dependencies, WithCommands = true>` replaces the pair it formed with `DirectlyRegistrableKeys`, whose only difference was checking against the raw dependency record instead of the augmented one — the same question, one hop shallower. `RegistrableKeys<Spec, Deps, false>` is that type now, and `SiblingCommands` builds its key set from it. `AugmentedDependencies` carries the same flag, and is where the recursion terminates. Behaviour is identical: the proof still caps at one hop, and the runtime still composes without limit. `DirectlyRegistrableKeys` was internal (never on any barrel), so no published name was removed
- **`AnyCommandClass`, `CommandRegistrySpecBase`, `CommandRunner`, `DepsOfClass`, `PayloadOfClass` and `ResultOfClass` moved to `application/command/types/`.** All six describe a *command class*, which is the command pillar's own vocabulary — and a command's `Siblings` declaration needs them at its factory call site, long before any registry exists. Leaving them in `command-registry/types` would have made `application/command` import from `application/command-registry`, which already imports `CommandResult` back from it: a cycle between the two pillars. **No public path changed** — `@roastery/beans/application/command-registry/types` re-exports the three public names and keeps serving them

### Fixed

- **`SchemaVO.validate` never ran its own schema.** It overrode `validate()` without calling `super.validate()`, so `SchemaSchema` was skipped entirely and a non-string value was rejected only incidentally, by `isSchema` failing on it
- **`SchemaVO.match` threw a bare `SyntaxError`** on a wire string that is not JSON, despite ending in a `return false` that suggested otherwise. It now raises `InvalidPropertyException` with the original preserved as `cause` — "that is not a schema" and "that did not match" are different answers, and the second must not silently absorb the first. The unreachable `return false` is gone with it

- **`inMemoryRepositoryOf` would have generated filter methods no port declares.** `testing/helpers/filter-keys-of.ts` excluded nested aggregates with a *negative* test (`!(… instanceof Entity)`), which a record-valued key passes — so the double would have grown a `findByMoney`/`countByMoney` while `RepositoryFilterKeysOf` excluded it. It now selects **positively**, with `isValueObjectClass`, matching how the type side already selects and staying correct against a fourth property kind. A new drift guard pins the two halves together in both directions

## [0.4.0] - 2026-08-20

### Added

- **`Command`, a new application-layer base class, and `@roastery/beans/application`, its pillar.** Built like an `Entity` — a blueprint resolved through explicit value → rule `default` → rule `derive`, with `blueprint(shape).with(rules)` reused unchanged — but value-object-only, with no identity and no mutation. A `Command` is constructed once (validating synchronously), then `execute(deps): Promise<CommandResult<Result>>`, the one place I/O and side effects belong. `CommandResult<Result>` is `{ result, events }`, `events` always an array: a command only ever *collects* what an entity raised, it never publishes. Reachable from the root barrel alongside `Entity`, `ValueObject`, `blueprint` and `DomainEvent`
- **`AggregateCommand`, `aggregateCommandOf` and `defineUseCase`** (`@roastery/beans/application/command`, `.../command/helpers`). The specialization for the case `Command`'s own docs already named but left manual — the result is a single aggregate and `execute()`'s last line is always `return collectResult(result)`. `execute()` is now inherited and the subclass writes `protected handle(deps): Promise<Result>` instead; `aggregateCommandOf` binds the blueprint the way `commandOf` does, and `defineUseCase` is that same function under a friendlier name, for a consumer who doesn't want the DDD vocabulary
- **`collectDomainEvents(...aggregates)` and `collectResult(result, ...rest)`**, the glue between `Entity.raiseEvent` and `CommandResult.events`. The first drains one or more buffers and concatenates them in call order; the second collapses `{ result: entity, events: collectDomainEvents(entity) }` into one call. Both are typed structurally (`{ pullDomainEvents(): readonly IDomainEvent[] }`) rather than against the concrete `Entity` class, which a concrete blueprint is not assignable to. `collectDomainEvents` always pulls deep — not losing events before they reach a `CommandResult` is the whole reason it exists
- **`Command`'s own input-validation failures throw application-layer exceptions.** A property failing validation during construction throws `UnprocessableContentException` (422) instead of the `ValueObject`'s `InvalidPropertyException`, preserved as `cause`; `fromJSON` rejecting a mis-shaped payload throws `BadRequestException` (400) instead of `InvalidDomainDataException`. Both fix `[Layer]` to `"application"`, so middleware can tell a command's own bad input apart from a deeper domain invariant. Definition-time mistakes (a `defineCommand` class field, a colliding key, an unknown `get` key) stay domain-layer
- **`entityOf(properties, source, extra?)` and `commandOf<Shape, Deps, Result>(properties, source, extra?)`**, factories returning a base class already bound to a blueprint. The subclass then declares only its own behaviour: `defineEntity`/`defineCommand`, the `interface X extends AccessorsOf<…> {}` declaration merge and its `biome-ignore` all go away, and the accessors come out typed **without** the merge — which matters, since forgetting that one line is the package's only silent failure mode
- **`commandRegistry(spec).withDependencies(dependencies)`, and `@roastery/beans/application/command-registry`, its pillar** (also reachable from `@roastery/beans/application`). Two-phase for the same reason `blueprint` is; `.get(key)` returns a ready-to-run bound function that constructs the command and `execute()`s it. The gate — only keys whose declared `Deps` the record structurally satisfies — is compile-time only, since `Deps` has no runtime footprint. Every command additionally receives a `commands` bag of its **siblings**, so a use case can reuse an already-registered one instead of duplicating it; the bag's *type* is proven one hop deep, while the runtime composes without limit and throws `LoopDetectedException` (508) on a key that reappears in its own call chain
- **`eventedRegistry(spec, emitter, options?)`, and `@roastery/beans/application/evented-registry`, its pillar.** `commandRegistry` gaining event behaviour: every event a `CommandResult` carries is published through the injected `IEventEmitter`, and reactions registered with `.on(eventClass, handlerClass)` run — `await`ed and isolated — before the command call resolves. It delegates construction and execution to a real `commandRegistry` underneath rather than reimplementing it. Matching a raised event against a registered class is by `name`, never `instanceof` (`raiseEvent` spreads the event into a plain object before buffering it). A throwing reaction never rejects the `CommandResult` of the command that raised the event — it goes to the optional `onError` hook, or a microtask re-throw — and a reaction chain cycling back onto a key or event name already on its chain raises `LoopDetectedException` instead of exhausting the stack
- **`defineEventHandler(handle, name?)`**, building an `IEventHandler` class from just its `handle` function — the `(args) => class` idiom `defineDomainEvent`/`defineValueObject` already use. Two overloads, so the event may be given either as an instance type or as the class itself (`defineEventHandler<typeof BeanPlanted, Deps>(...)`), removing the `InstanceType<…>` boilerplate `IEventHandler`'s own docs named as a trap. `Deps` defaults to `unknown`, not `Command`'s `void`, since the registry's gate checks that what it supplies *extends* what the handler declares
- **`RepositoryOf`, a type generator, and `@roastery/beans/domain/repository/types`, its pillar.** Builds a repository port for one entity from a spec of the methods it needs, checked against a catalog derived from that entity's **own blueprint**: `findByEmail` is offered because the entity declares `email`, its argument is `string` because that key is an `EmailVO`, and both disappear the moment the key is renamed. The granular `ICan*` contracts it fuses are the unit a use case asks for — a command declaring `Deps = { users: ICanReadId<typeof User> & ICanUpdate<typeof User> }` has `delete` *unavailable* rather than merely discouraged. **Type-only, entirely**: no factory, no symbol, no runtime, `dist/domain/repository/types/index.js` is 0 bytes
- **`countBy{Key}` and `existsBy{Key}` on the generated port.** `count()` takes no filter, so a filtered list had a page size and a page number but no total; `existsBy{Key}` is the check every `create` guarding a unique key makes, which an adapter otherwise emulates by hydrating a whole aggregate to answer a question about its existence. They differ over `id` alone, deliberately: `existsById` exists (the primary-key check an insert makes), `countById` does not — its answer is always 0 or 1, the same reasoning that already excludes `findManyById`. New public types: `ICanCountBy`, `ICanExistsBy`
- **`RepositoryPageOf<EntityClass>` and `RepositoryOrderKeysOf`: a collection read declares its order.** A page is a slice, and a slice of an unordered set can repeat or skip a row between two calls — which a real database does and a `Map`-backed double hides, so the failure only ever appeared in production. `page`/`perPage`/`orderBy`/`direction` are all required, and `orderBy` is narrowed to keys carrying a **single scalar**: an array- or object-valued key is filterable (`deepEquals` defines equality for it) but has no total order in JavaScript or in `jsonb`, so ordering by one would compile and then differ per adapter. `findManyByIds` is unaffected and still takes no page — `ids` bounds it and fixes its order
- **A sensitive value-object suppresses its key's lookup methods in `RepositoryOf`.** A blueprint holding a `PasswordVO` used to derive `findByPassword`, `findManyByPassword`, `countByPassword` and `existsByPassword` — a generated port inviting the one query the declaration exists to prevent, the boolean half arguably the worst of them, handing out the secret one bit at a time. All four now disappear, at the type level and in `inMemoryRepositoryOf`'s runtime alike, from one insertion point (`RepositoryFilterKeysOf`). **Writes are untouched** — the point is to remove a lookup, not to make the field unstorable — and the rule is closed on both doors: `Extras` is constrained by the new `RepositorySuppressedNamesOf`, so a hand-written extra cannot declare a suppressed name back onto the port. **Only the value-object source suppresses**: `sensitive: ["token"]` on `defineEntity`/`entityOf` still redacts and still answers `isSensitive`, but its literal does not survive into the class type, and making one form suppress and not the other would split two spellings the package holds equivalent on purpose
- **`inMemoryRepositoryOf(entityClass, spec?, handler?)`, and `@roastery/beans/testing`, its subpath.** Generates a working in-memory repository from an entity's blueprint, typed as **the very same `RepositoryOf` port** a real adapter implements — not a parallel test interface to keep in sync, so a double is substitutable by construction. The spec applies at runtime as well as in the type, and an empty or omitted one means the whole catalog. The `handler` argument is the runtime counterpart of `Extras`: it receives every generated method plus `rows` and `hydrate`, and its return is merged **over** them, so a colliding name replaces one while still reaching the original underneath. The double is **faithful, not convenient** — it stores `toJSON()` and rehydrates through `fromJSON` on every read, so mutating after `create` does not persist, and its writes behave like a database rather than a `Map`: `create` throws `ConflictException` on a taken `id` or unique value, `update`/`delete` throw `ResourceNotFoundException` when no row carries the id. The unique scan follows SQL rather than convenience — a nullish value never conflicts, comparison goes through `deepEquals` and never `===`, and `update` excludes the row it is writing. `src/testing/` is the first runtime in `beans` outside the two layers, behind its own subpath precisely so a production bundle never reaches it, and the only place importing `@roastery/terroir/exceptions/infra`
- **`NodeEventEmitterAdapter`, and `@roastery/beans/node`, its subpath.** Node's `EventEmitter` wrapped to satisfy `IEventEmitter` — the boilerplate that was being retyped at every call site. Its whole job is negative: every `node:*` import in the package lives behind this one subpath, so `domain`/`application` stay usable from a worker or an edge function. It special-cases exactly one name, and has to: emitting `"error"` with no listener throws `ERR_UNHANDLED_ERROR`, which — since `eventedRegistry` `await`s `emit` while publishing — would reject the `CommandResult` of a command that actually succeeded. With zero listeners the adapter returns early, which is what an emit already is on any other name
- **`@roastery/beans/way`, a curated re-export barrel — "the Roastery Way."** One import path for the low-ceremony subset: `blueprint`, `entityOf`, `defineDomainEvent`, `defineUseCase`, `defineEventHandler`, `commandRegistry`, `eventedRegistry`, plus the `IEventEmitter` and `RepositoryOf` types. **Not a third layer** — `src/way/index.ts` contains zero logic, only `export { X } from "..."` lines, and every name stays reachable at its original subpath. Both registries are exported deliberately: `eventedRegistry`'s emitter parameter is required, so it asks the reader to decide where events go before they have necessarily met domain events, while `commandRegistry` gives up nothing (same spec, same `.get()`, same `events` array) and is what `eventedRegistry` is built on. The ~45-name value-object catalog sits one level deeper, at `way/collections/value-objects` (+ `/optional`, `/nullable`, `/custom`)
- **`@roastery/beans/domain/entity/decorators`, three standard (TC39) class decorators**: `onCreate`, `onUpdate`, `onDelete` — each raises a declared, payload-less `DomainEvent` at one point of the lifecycle, so a subclass stops calling `raiseEvent` by hand there. `onCreate` fires on a fresh construction (including `.demo()`), decided by the same `extractIdentity` rule the base constructor applies, so a hydration raises nothing; `onUpdate` fires when `set`/`setMany` actually changed something; `onDelete` fires the first time `destroy()` is called. Stacking them needs no coordination — each overrides only its own method and delegates the rest through `super`. There is deliberately no `onRead`/`onHydrate`: rebuilding an entity from storage is not a domain fact, and since a repository hydrates through `fromJSON`, such an event would ride along in every `CommandResult`
- **`emit` and `onError`, two standard (TC39) method decorators**, for an arbitrary `Entity` method rather than a fixed lifecycle point. `emit(Event)` raises once the method body returns and never if it throws — no `try`/`catch` is involved, the `raiseEvent` written after the call simply never runs. `onError` is the one decorator here that catches: it builds an event from the caught error — either from a `BareDomainEventClass` or from an `(error) => IDomainEvent` factory, told apart structurally by `isBareEventClass` since both are functions — raises it, and **always re-throws the original**. The event is a side channel, never a way to swallow a failure. Note `emit` shares its name with `IEventEmitter.emit` one layer up and does something different: this one raises into the entity's own `[Events]` buffer
- **Sensitive values are kept out of logs, declaratively and configurably.** `IValueObjectMetadata` gained `sensitive` — a flag that travels with the class, so a `PasswordVO` is secret in every blueprint using it — plus `redactWith`, that class's own replacement; `defineEntity`/`defineCommand` gained `sensitive?: readonly Key[]` for the case the type alone does not settle (a `StringVO` holding an API token). `configureRedaction` sets the global placeholder. Where the replacement lands is deliberately asymmetric: **`Command.toJSON()` redacts** (never persisted, and `toJSON` is what a structured logger reaches through `JSON.stringify`), **`Entity.toJSON()` does not** (persistence contract, must round-trip through `fromJSON`) and offers `toSafeJSON()` instead, which recurses so each nested entity applies its own keys; `toString()` and the `inspect` hook redact on both. `PasswordVO`, `OptionalPasswordVO` and `NullablePasswordVO` now all declare it — only the first ever had
- **`Entity#isSensitive(key)` and `Entity#isUnique(key)`, plus `uniqueKeysOf(entityClass)`.** Both predicates report the *declaration*, never the stored value, and both throw `InvalidPropertyException` for a key outside `blueprint ∪ id/createdAt/updatedAt` rather than answering `false` — a predicate that shrugged at a typo would turn it into a silent "not a secret" / "not unique". They diverge in one place, on purpose: `isUnique("id")` is always `true` (identity is the primary key), `isSensitive("id")` always `false` (an identifier is what makes a log useful). `uniqueKeysOf` asks the same question of the **class**, before any instance exists — when a repository is deciding which columns need an index — through the same construction-free `Object.create` probe `fromJSON` uses
- **`unique`, a new field on a value-object's `defineMeta()` and on an entity's `defineEntity()`.** Declares that a value must not repeat across the rows of the aggregate holding it — the most common invariant an entity carries and the one it structurally cannot check, since uniqueness is a property of the *set*. Mirrors `sensitive` in both declaration sites (`unique: true` on the VO for "this kind of value is always unique"; `unique: ["handle"]` on the entity when the type alone doesn't settle it) and rides into all eight custom-VO factories for free through `IValueObjectHooks`. **Purely declarative**: nothing validates it at construction, and enforcement belongs to whoever implements the port. `CommandDefinition` deliberately does not gain it — a command is never persisted. Unlike `sensitive`, it stays a plain `boolean` and suppresses nothing from the port, since nothing at the type level reads it
- **A full numeric grid in `domain/collections`: `Integer` and `Double` alongside `Number`**, each unconstrained, `Positive*` and `Negative*` — 8 schemas, 8 value-objects and their 16 `Optional*`/`Nullable*` variants. The catalog previously offered one numeric shape and it could not say "whole number" (so an adapter reading a derived schema had no way to pick an integer column). `IntegerSchema` is `t.Integer`, emitting `type: "integer"` rather than `customNumberVO`'s `multipleOf: 1`; `Double*Schema` is structurally identical to `Number*Schema` and deliberately so, since JSON Schema cannot express "floating point" — what makes a `Double*VO` decimal is its `transform`, not its schema. **Both families normalise rather than reject**, the way `SlugVO` slugifies: `Integer*VO` truncates toward zero, `Double*VO` rounds to two places, both before validation. **`Positive*` and `Negative*` both include zero** — read them as "non-negative"/"non-positive"; the unconstrained form is what to reach for when zero must not be special. Both transforms normalise `-0` to `0`, which is not cosmetic (`JSON.stringify(-0)` is `"0"` while `Object.is(-0, 0)` is `false`, so an un-normalised `-0` fails its own round-trip), and `toDouble` carries one documented infidelity: decimal rounding over a binary float is approximate, so `1.005` rounds to `1`. Reach for a decimal library at the boundary when exact decimal arithmetic is a domain requirement
- **`customDoubleVO(args?)`, a new custom value-object factory.** The catalog's `Double*VO` classes are fixed at two decimal places, which is right for money and wrong for a latitude or a rate. `decimals` (default `2`) rides in its own args interface (`IDoubleValueObjectArgs`) rather than in `options`, because it is not a TypeBox option — JSON Schema cannot express fixed decimal precision, and the constraint is enforced by the generated `transform`. There is deliberately no `customIntegerVO`: `defineValueObject({ schema: t.Integer(…) })` already is that
- **`unionVO(schemas, args)`, a new custom value-object factory** — the general form of `optionalVO`/`nullableVO`, for the case the alternatives are *domain* values rather than emptiness (a document number issued as a formatted string by one registry and a plain integer by another). `schemas` is a `const` type parameter, so an array literal needs no `as const`. `default` is required, as in `customObjectVO`: no placeholder can be guessed for an arbitrary union
- **`customBinaryVO(args?)`, a new custom value-object factory, plus its `encodeBase64`/`decodeBase64` helpers.** The way to declare a property holding bytes. **Its value is a base64 `string`, not a `Uint8Array`, and that is the whole design decision**: `toJSON()` emits a value-object's `value` as-is, so a binary value would leave `JSON.stringify` as `{"type":"Buffer","data":[…]}` and `fromJSON` would reject it — the round-trip guarantee breaking on precisely the kind of property that exists to be persisted. `minBytes`/`maxBytes` are checked against the **exact** decoded size in the generated `validate`, never lowered into `minLength`/`maxLength`, since a four-character base64 group carries one, two or three bytes. The helpers are built on the Web-standard `btoa`/`atob`, keeping `domain/` runtime-agnostic
- **`defineDomainEvent(name)`**, building a payload-less `DomainEvent` class from just its name — the same "factory returns a class" idiom the custom-VO factories use, applied to the one-method subclass such an event otherwise requires. Its constructor is exactly `(aggregateId: string)`, so it drops straight into `raiseEvent`'s bare-class form and into the decorators, which accept only that shape. Call it once at module scope: each call mints a fresh class
- **`Entity.pullDomainEvents({ deep: true })`**, draining this entity's buffer and then each nested entity's, recursively, in blueprint order. The no-argument form is unchanged and still shallow. The motivating case is a nested entity carrying lifecycle decorators: `onCreate` fires every time the parent is constructed, and a shallow pull from the root left those events in a buffer nobody read
- **`Entity.destroy()`/`Entity.isDestroyed`.** A lightweight marker, not a hard guard: `destroy()` flips a private field and releases the transient `[Storage]`, idempotently, but `get`/`set`/`toJSON` keep working afterwards. Nothing can force garbage collection from inside the entity, so "removed from memory" means the cache is released and the fact recorded
- **`EntityHas<EntityType, ExpectedShape>` and `entityHas(entityClass, expectedShape)`**, the compile-time and runtime checks for whether a blueprint carries a given set of fields, each backed by (or aliased from) a specific `ValueObject` class. Meant to compose with a conditional type; the `repository` pillar is what that `@example` was pointing at all along
- **`blueprint(shape).done()`**, closing a rule-less blueprint. It returns the shape *as given* — same object reference, no `Rules` slot — so it is indistinguishable from the plain literal that always worked. It replaces `.with({})`, which read like a rule map somebody forgot to fill in, and lets every blueprint open and close the same way
- **`@roastery/beans/application/collections/*`**, a thin alias mirroring every `@roastery/beans/domain/collections/*` subpath, so a `Command` blueprint never imports from the domain layer's subpaths directly — the same classes, re-exported. Both this alias and `way`'s now carry a spec pinning them to the original: name parity read from the barrels' *source* (so the type-only `custom/types` subpath is covered, where an `Object.keys` comparison would pass vacuously) and reference identity at runtime, which catches a barrel that *redeclares* a class instead of re-exporting it — every name lined up while `instanceof` quietly breaks
- **`src/shared/helpers/`, one copy of what both pillars use verbatim**: `installAccessors`, `applyRuleDefaults`, `rulesOf` and `isValueObjectClass`. All were duplicated per pillar and byte-identical, so the copies only guaranteed that a fix to one would silently miss the other. The directory carries no barrel on purpose — `exports` maps `./*` onto `dist/*/index.d.ts`, so a barrel is what makes something public. `readDefinition` stays duplicated: its whole content is the pillar-specific method name and message
- **A `Known limits` section in the README, and `bun run example`.** `Known limits` gathers what was scattered per pillar or documented only in `CLAUDE.md`: events publishing before any commit, the structurally-but-not-exactly checked dependency gate, sibling composition proven one hop deep, the double's reference identity and ordering, the `sensitive` asymmetry, and the accessor merge. `bun run example` runs `examples/user-flow.ts`, the end-to-end dogfooding script that used to sit at the root as `testing.ts` and now type-checks with everything else

### Changed

- **BREAKING** — **`src/` split into `domain/` and `application/`, and every existing subpath moved under `domain/`.** `@roastery/beans/entity` → `@roastery/beans/domain/entity` (with all of its `/helpers`, `/types`), `@roastery/beans/value-object` → `@roastery/beans/domain/value-object`, `@roastery/beans/domain-event` → `@roastery/beans/domain/domain-event`, `@roastery/beans/collections/*` → `@roastery/beans/domain/collections/*`. The root barrel is **unaffected**. No behaviour change to any class or helper, only where it is imported from — the rename table above is the whole of it
- **BREAKING** — **`NumberSchema` no longer carries `minimum: 0`, so `NumberVO` accepts negative values.** The constraint was there from the start with no justification beyond the description restating it, and it made the most generically-named class in the catalog quietly mean something narrower: a blueprint could not declare a balance, a delta, a temperature or a coordinate without leaving the catalog for `customNumberVO`. **This is the one break in this release that fails silently rather than at compile time** — nothing about a `NumberVO`-backed key changes shape, so a blueprint relying on negatives being rejected now accepts them and the first symptom is bad data. The migration is mechanical: every previous use of `NumberVO` meant `PositiveNumberVO`, which is that exact schema under a name that says so. `OptionalNumberVO`/`NullableNumberVO` inherit the widening, with `Optional`/`NullablePositiveNumberVO` as their replacements
- **`IValueObjectMetadata` and `ValueObject` gained a third type parameter, `Sensitive extends boolean = false`.** `sensitive` as a plain field was invisible to the compiler — `defineMeta` is `protected` and only ever invoked at runtime — and carrying the literal into the `[Meta]` slot is what makes the port suppression above expressible at all. Existing declarations are unaffected by the default; a sensitive value-object must now spell it out (`extends ValueObject<string, typeof PasswordSchema, true>`), and the default being `false` rather than `boolean` is deliberate: it makes `sensitive: true` without the parameter a `TS2322` rather than a flag that silently does half its job. All nine factories **infer** the literal, so an inline `customStringVO({ sensitive: true })` needs no ceremony, while `metaOf`/`readMeta` take the opposite default (`= boolean`) — they are the reading side, and a caller inspecting an unknown class must be able to compare `meta.sensitive === true`
- **`set`/`setMany` now return a `boolean`** — the change flag they already computed to decide the `updatedAt` stamp, which `onUpdate` reads to know whether anything actually changed. Comparing `updatedAt` before and after looked equivalent and was not: the stamp has millisecond resolution, so two distinct mutations in the same tick compared equal and the second event was swallowed. `IEntity` reflects the new return type; callers ignoring it are unaffected

### Fixed

- **`fromJSON` no longer rejects a payload that simply omitted an `optionalVO`-backed key.** `modelFor` (both pillars) put every blueprint key in the schema's `required` list, including those whose value-object accepts `undefined`. `toJSON()` emits such a key as present-with-`undefined`, which `JSON.stringify` then drops — so a payload that made a real round-trip came back missing it and was rejected. `Command.fromJSON` was the worse of the two, being the documented entry point for an untrusted HTTP body: a client omitting an optional field got a 400. Those properties are now emitted through `t.Optional`, decided per property by asking the schema itself whether it accepts `undefined`
- **A nested entity's payload is now relaxed at every depth, not just the first.** `NestedEntityInput` derived from the serialized form and stripped `keyof IRawEntity` only at the outermost level, so a *grandchild* still demanded its own `id`/`createdAt` and the keys its blueprint rules cover — a three-level aggregate was a compile error even though the runtime accepted it and generated the identity correctly. It is now `ConstructionValuesOf<Shape>`, the same type the top level uses, so "a complete payload" means one thing at every depth

## [0.3.0] - 2026-08-17

### Added

- **`Entity.raiseEvent`/`Entity.pullDomainEvents`.** Domain events, buffered per instance behind the new `[Events]` slot and drained explicitly — nothing dispatches them, `beans` stops at the buffer, whatever happens with the drained array is the consuming application's call. `raiseEvent` (`protected`) takes only `name` plus whatever payload the caller's event carries; it stamps `occurredAt` and `aggregateId` itself, from `DateTimeVO.now` and the entity's own `id`, so every event carries at least its raising entity's identity and no subclass can override either field — `beans` is not event-sourced, so there is no replay path that would need to. Never fires on its own: `set`/`setMany` do not raise events, only an explicit call from a subclass's own business method does. Only the aggregate root should call it — an event raised inside a nested entity stays in that nested entity's own buffer, since `pullDomainEvents` does not recurse through `[Context]` the way `toJSON` does. `pullDomainEvents` (`public`) returns everything buffered since the last pull, oldest first, and empties the buffer. Starts empty on all three construction paths (`new`, `fromJSON`, `demo`), same guarantee as `[Storage]`, and never reaches `toJSON()` or the schema. `IEntity` grew a matching `pullDomainEvents()` member. `raiseEvent` also accepts a **bare class reference** in place of a built event — `this.raiseEvent(OrderConfirmed)` instead of `this.raiseEvent(new OrderConfirmed(this.id))` — for any `DomainEvent` subclass whose constructor takes only `aggregateId`; the base instantiates it itself, passing `this.id`. A subclass whose constructor needs more than `aggregateId` isn't assignable to that shape, so TypeScript routes it to the already-built branch and rejects the bare form at compile time — the constructor signature is the guard, no runtime check needed
- **`@roastery/beans/domain-event`, a new pillar.** `IDomainEvent` (`.../domain-event/types`) is the `{ name, occurredAt, aggregateId }` contract `Entity.raiseEvent` builds, and `DomainEvent` (`.../domain-event`) is an optional abstract base for writing concrete event classes against it: a subclass declares only `defineName()` — the event's stable, dot-namespaced name — and passes `aggregateId` up through `super()`; `occurredAt` is stamped by the base itself, the same `DateTimeVO.now` stamp `Entity.raiseEvent` uses. Sugar over `IDomainEvent`, not a replacement for it — `raiseEvent` already accepts a plain `{ name, ...payload }` object and stamps `occurredAt`/`aggregateId` on its own regardless of what it's given, so `DomainEvent` only pays off for events with their own payload fields, where a class reads better than repeating the object literal at every call site, and lets an event be constructed and inspected on its own, without an `Entity` in the loop. `defineName` follows the same **prototype-method, never a class field** rule as `defineMeta`/`defineEntity`, guarded at runtime with the same `InvalidEntityDefinitionException`
- Bumped the `@roastery/terroir` dependency to **0.2.1**, which now ships the `Events` slot symbol (`@roastery/terroir/symbols`) alongside the other seven — the same move `Rules` made in terroir 0.2.0 (see `[0.2.0]`, below). `Entity`'s domain-event buffer keys off it directly; this package ships no local symbol file for it

### Changed

- **`blueprint` and `DomainEvent` are now also reachable from the root barrel** (`import { blueprint, DomainEvent, Entity, ValueObject } from "@roastery/beans"`), and `blueprint` from `@roastery/beans/entity` alongside `Entity` too — both were already public (`@roastery/beans/entity/helpers` and `@roastery/beans/domain-event` respectively, still valid), this only widens where they're reachable from, since a blueprint with rules is typically declared right next to its `Entity` subclass. No behavior change

## [0.2.0] - 2026-08-15

### Added

- **`Entity`, rebuilt.** The blueprint-driven base (formerly `BetterEntity`) is now _the_ `Entity`, exported from `@roastery/beans` and `@roastery/beans/entity`. Subclasses declare a blueprint (`{ field: SomeVO }`) and a `defineEntity()` method; the base derives validated construction (with optional all-or-nothing identity), `toJSON`/`fromJSON` (the latter a strict static that validates the whole payload first), atomic `set`/`setMany` with a single automatic `updatedAt` stamp, read-only accessors typed via `AccessorsOf`, an aggregate TypeBox schema memoized per class, `demo()` fixtures, nested-entity aggregates with cycle detection, and the `[Storage]` transient store
- **`ValueObject`, rebuilt.** The self-validating base (formerly at `value-object/new.ts`) is now _the_ `ValueObject`: subclasses declare only `defineMeta()` (`{ default, schema }`) and optionally override `transform()`; validation runs in the constructor, so no instance exists unvalidated. `demo(context)` builds from the declared default, which may be a thunk for expensive values
- **Blueprint rules.** `blueprint(shape).with(rules)` (from `@roastery/beans/entity/helpers`) declares a blueprint that carries the domain's own rules: `{ default }` for a fallback belonging to the _entity_ rather than to the value-object, and `{ derive }` for a property computed from its siblings. Ruled keys become optional in the constructor payload, so the domain's defaults and derivations stop needing a hand-written constructor — which is also what keeps `fromJSON`/`demo()` intact, since a custom constructor is exactly what breaks them. Precedence is explicit value > `default` > `derive`; derivations run in blueprint order over already-normalised siblings; rules apply in `demo()` (fixtures stay coherent) and to a **nested** entity's payload, but never re-fire on `set`/`setMany`; the derived schema and `fromJSON`'s strictness are untouched. Declaring both `default` and `derive`, or naming a property outside the blueprint, is a compile error and an `InvalidEntityDefinitionException` at runtime. New public types: `PropertyRule`, `RulesOf`, `RuledBlueprint`
- The `Rules` slot symbol, declared **temporarily** in this package (`src/entity/rules.symbol.ts`) instead of `@roastery/terroir/symbols`, where it belongs. It is the single exception to the repository's "never declare a slot symbol locally" rule and exists to be deleted — `docs/terroir-rules-slot.md` tracks the move to terroir 0.2.0
- **Custom value-object factories.** `@roastery/beans/collections/value-objects/custom` ships functions that return a `ValueObject` **class** rather than an instance, so a blueprint can declare a constrained property inline instead of paying a schema plus a subclass for every domain rule: `customStringVO`, `customNumberVO`, `customArrayVO` (item schema as its first argument), `customObjectVO` (declared shape, `additionalProperties: false`), `customRecordVO` (free-form bag), and the core `defineValueObject` they all lower into — reach for that one when the schema already exists. Ready defaults are validated **inside the factory call**, so a placeholder the options reject (`customStringVO({ options: { minLength: 8 } })`) raises `InvalidEntityDefinitionException` at import time rather than at the first `demo()`; thunk defaults stay lazy and are validated by the base in demo mode. `customObjectVO` requires an explicit `default`, since no placeholder can satisfy an arbitrary set of required properties. Each call mints a fresh schema and a fresh class, so factories belong at module scope: calling one inside `defineEntity()`/`defineMeta()` defeats the compiled-validator and aggregate-model caches, both keyed by object identity. New public types under `@roastery/beans/collections/value-objects/custom/types`: `ValueObjectClassOf`, `IDefineValueObjectArgs`, `ICustomValueObjectArgs`, `IValueObjectHooks`

- `@roastery/beans/entity/types` grew the blueprint type surface: `IEntity` (the rebuilt contract), `AccessorsOf`, `EntityDefinition`, `PropertiesShapeBase`, `RawContextOf`, `SerializedEntity` (plus the supporting aliases as internal one-type-per-file modules)

### Changed

- `Entity`/`IEntity`'s abstract `[EntityFactory]` method now returns `Entity<SchemaType>` / `IEntity<SchemaType>` instead of `this`. Existing subclasses that implement it as `[EntityFactory](data, initialProperties?): this` are unaffected (still a valid covariant override), but a subclass is no longer required to route through `this` at all — it can implement `[EntityFactory]` as a one-line delegate to a plain `public static build: EntityFactory<Subclass, SubclassInput>` value (e.g. `public [EntityFactory](data, initialProperties?) { return Subclass.build(data, initialProperties); }`), keeping the actual rebuild logic in an ordinary static factory instead of an instance method
- `EntityUpdater.run` asserts the rebuilt entity as `EntityType` when invoking `[EntityFactory]` — a consequence of the return type above no longer being `this`, generic code holding an `EntityType extends IEntity<t.TSchema>` only sees the widened base return from the type system, so the assertion (backed by the existing `id`/`createdAt` identity check) restores the concrete type

## [0.1.2] - 2026-07-06

### Added

- `EntityFactory` symbol (exported from `@roastery/beans/entity/symbols`) — abstract self-rebuild method every `Entity` subclass must implement as `[EntityFactory](data, initialProperties?): this`, so generic consumers holding an entity instance (e.g. `EntityUpdater`) can rebuild it without a separately-wired factory function

### Changed

- **BREAKING:** `Entity`/`IEntity` now declare `[EntityFactory]` as an abstract instance method; every concrete entity subclass must implement it (typically `return new Subclass({ ...(initialProperties ?? makeEntity()), ...data }) as this;`)
- **BREAKING:** `EntityUpdater`'s constructor no longer takes an `entityFactory` second argument (`new EntityUpdater(entity)` instead of `new EntityUpdater(entity, entityFactory)`) — it now calls the entity's own `[EntityFactory]` method to rebuild after each mutation

## [0.1.1] - 2026-07-05

### Added

- `EntityUpdater` (exported from `@roastery/beans/entity`) — stateful field-level updater that round-trips the entity through the `Mapper` (serialize → mutate → validate against `[EntitySchema]` → stamp `updatedAt` via `DateTimeVO.now` → rebuild through an `EntityFactory`). Accumulates updates (`updater.current` exposes the latest instance), skips the `updatedAt` stamp for structurally-equal or VO-normalized no-op values, rejects base-prop updates (`id`/`createdAt`/`updatedAt`) at the type level and at runtime, and throws `OperationFailedException` when the factory fails to preserve the entity's identity
- `EntityFactory` type (exported from `@roastery/beans/entity/types`) — factory signature `(data, initialProperties?) => Entity` used by `EntityUpdater` and by `Mapper.toDomain`-style reconstruction
- `EntityDTOOf` and `EntityUpdaterInput` types (exported from `@roastery/beans/entity/types`) — resolve an entity type's plain-object DTO shape and its domain-content slice; `EntityUpdaterInput` is the input shape `EntityUpdater` requires of its factory
- `deepEquals` (exported from `@roastery/beans/entity/helpers`) — structural equality over JSON-shaped DTO values, used by `EntityUpdater` to detect and skip no-op updates

### Changed

- Biome schema reference in `biome.json` bumped from `2.4.11` to `2.4.16`

- `Mapper.toDomain` `Input` generic parameter with default `Omit<t.Static<SchemaType>, keyof IRawEntity>` so callers can constrain the domain-content slice independently from the full schema, and the DTO parameter is now typed as `Input & IRawEntity` (closes #6)

- `EntityStorage.set` returns the stored value to support inline chaining (closes #4)

### Changed

- **BREAKING:** `Entity` constructor now requires the entity-type tag as a second argument (`super(data, "post")`); `[EntitySource]` is no longer `abstract` and must not be declared as a class field on subclasses. Previously the abstract field was assigned via a subclass class-field initializer, which only runs after `super()` returns — meaning any `InvalidPropertyException` raised by the value-objects built during base-class construction had no `source` set. The new shape propagates the tag _before_ any validation runs, so error context is always available (closes #3)
- `Entity._id` and `Entity._createdAt` are now `private readonly` (write-once, only assigned by the constructor)
- All eight collection value objects (`BooleanVO`, `DateTimeVO`, `DefinedStringVO`, `SlugVO`, `StringArrayVO`, `UrlVO`, `UuidArrayVO`, `UuidVO`) declare `schema` as `protected override readonly`, matching the `protected abstract readonly` contract on the `ValueObject` base
- `Mapper.toDomain` implementation no longer casts the DTO through `as IRawEntity & Record<string, unknown>`; the destructuring leans on the new `Input & IRawEntity` parameter type, so the domain-content cast collapses to a single `content as Input`
- Re-exports in `collections/schemas/index.ts` and `collections/value-objects/index.ts` are now sorted alphabetically
- `entity-storage.test.ts` renamed to `entity-storage.spec.ts` to match the rest of the suite

### Fixed

- `InvalidPropertyException` raised during `Entity` base-class construction now carries the correct `source`. Previously the source was `undefined` for the very first validation pass because the abstract class-field had not yet been initialised (closes #3)
- `IdObjectDTO.examples` mistakenly used `{ uuid: "..." }` despite the schema shape being `{ id: UuidDTO }` — corrected to `{ id: "..." }` and the description tightened to drop the redundant "by its UUID" wording
- README imports updated to the actual subpath layout (`/entity/symbols`, `/entity/decorators`, `/entity/factories`, `/entity/helpers`, `/entity/services`, `/entity/dtos`, `/entity/types`, `/value-object/types`); the previous version listed every helper as living at `@roastery/beans/entity`, which only re-exports the `Entity` class
- README `Post` example constructor now passes `entitySource` to `super(...)` and drops the redundant `[EntitySource]` class field, matching the real `Entity` signature
- README "Mapping conventions" table expanded with the missing rules: `Schema → toString()`, nested `Entity` recursion, and the `null` / `undefined` / primitives passthrough
