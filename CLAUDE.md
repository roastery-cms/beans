# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`@roastery/beans` is a TypeScript library that ships the DDD building blocks for the Roastery CMS ecosystem, split into two layers: a **domain** layer (a blueprint-driven `Entity` base class, a self-validating immutable `ValueObject` base class, an optional `DomainEvent` base, and a `collections` module with ready-made Schema / Value Object pairs — UUID, slug, email, datetime, etc.) and an **application** layer (a blueprint-driven `Command` base class — the same construction/validation machinery as `Entity`, minus identity and mutation, for orchestrating domain behaviour behind a validated input — plus `AggregateCommand`, its specialization for the common single-aggregate-result case). The domain layer also carries a third, purely declarative pillar, `repository` — `RepositoryOf` plus the `ICan*` capability contracts, type-only, deriving a persistence port from an entity's own blueprint and emitting no runtime at all. `@roastery/beans/testing` is the one place that implements that port: `inMemoryRepositoryOf`, a blueprint-generated in-memory double, behind its own subpath so it never reaches a production bundle. All schema validation flows through `@roastery/terroir` (a TypeBox-backed schema/exception toolkit), currently on **0.2.1**, which also owns the well-known symbols keying the bases' slots. `@roastery/beans/way` is a third top-level entry that is **not** a third layer — a curated, re-export-only barrel spanning both, picking the low-ceremony entry points (`entityOf`, `defineDomainEvent`, `defineUseCase`, `defineEventHandler`, `eventedRegistry`) over the precise class forms next to them; see "Architecture" below.

The package is pre-1.0. Read `README.md` first — it stays in sync with the API and shows the canonical subclass patterns. `CHANGELOG.md` follows Keep a Changelog and is updated manually per release.

## Tooling

Bun is managed by **mise** (`mise.toml` pins `bun = "latest"`). Always invoke toolchain binaries through it — the husky hooks do the same:

```bash
mise exec -- bun run test:unit       # full unit suite
mise exec -- bun run test:coverage   # with coverage
mise exec -- bun test path/to/file.spec.ts        # single file
mise exec -- bun test --test-name-pattern "<re>"  # filter by it/describe name

mise exec -- bunx tsc --noEmit -p tsconfig.json   # type-check only (tsconfig has noEmit: true)
mise exec -- bunx biome check                     # lint without auto-fix
mise exec -- bun run knip                         # detect orphan exports/dependencies
mise exec -- bun run build                        # biome --fix && knip && tsup → dist/
mise exec -- bun run setup                        # build + bun link (for local linking into a consumer)
```

Test files use `.spec.ts` and live next to the file under test.

Husky enforces:
- **commit-msg**: commitlint with `@commitlint/config-conventional` — commits must follow Conventional Commits.
- **pre-commit**: `bun run test:unit` runs on every commit.

## Architecture

`src/` has two top-level directories, one per layer, each with its own pillars — plus `shared/`, `way/` and `testing/`. **None of those three is a layer**: `shared/` is internals both pillars need verbatim, `way/` a re-export-only barrel, `testing/` a time-of-use concern (and the only one of the three with runtime of its own). Each is documented in its own paragraph after the two layers, below:

**`domain/`**
- **`entity/`** — the `Entity` base (`domain/entity/entity.ts`), plus `helpers/`, `types/` and `decorators/`. The `EntityStorage` runtime class (`domain/entity/entity-storage.ts`) backs the `[Storage]` slot. `decorators/` ships three standard (TC39) class decorators — `onCreate`, `onUpdate`, `onDelete` — that raise a declared event at each fixed point of the lifecycle instead of the subclass calling `raiseEvent` by hand (see "Lifecycle decorators" below), plus three standard (TC39) method decorators — `beforeHandle`, `afterHandle`, `onError` — that raise a declared event immediately before/after an arbitrary instance method runs, or when it throws (see "Method decorators" below).
- **`value-object/`** — the `ValueObject` base (`domain/value-object/value-object.ts`), plus `helpers/` (`metaOf`, and the internal `readMeta`/`resolveDefault`) and `types/` (`IValueObjectContext`, `IValueObjectMetadata`, `ValueObjectClassLike`).
- **`domain-event/`** — `DomainEvent` (`domain/domain-event/domain-event.ts`), the optional abstract base for writing concrete domain-event classes, `defineDomainEvent` (`domain/domain-event/define-domain-event.ts`), a factory that builds a payload-less `DomainEvent` class from just its name, plus `types/` (`IDomainEvent`, the contract `Entity.raiseEvent` builds, and `DomainEventClassOf`, the class `defineDomainEvent` returns). Its own pillar, not nested under `entity/`, even though `Entity` is its only consumer today — `IDomainEvent` is a plain data contract, not entity-specific machinery.
- **`repository/`** — `repository/types/` only: `RepositoryOf` (`repository/types/repository-of.type.ts`), the port generator, and the nine `ICan*` capability contracts it fuses. **Type-only, with no `index.ts` at the pillar root** — there is nothing to export at that level, so `@roastery/beans/domain/repository/types` is the canonical subpath, paralleling `.../entity/types` and `.../command/types`; nothing changed in `package.json` for it (`exports["./*"]` + `tsup 'src/**/index.ts'` already cover any barrel), and `tsup` emits an empty `index.js` next to the `.d.ts`, exactly as it already does for `dist/domain/entity/types/`. `RepositoryOf<EntityClass, Spec, Mode, Extras>` maps each selected method name to its contract through `RepositoryContractOf` and fuses the result with `UnionToIntersection` (kept local to the pillar, not `shared/` — the house rule is "only what both pillars need verbatim moves up"). `UnionToIntersection<never>` is `unknown`, not `never`, so `RepositoryOf` guards with `[Selected] extends [never] ? never` *before* reaching it: without that, asking for the write half of a read-only spec would resolve to `unknown` and silently satisfy any `Deps` slot. Two mutually assignable spec forms — a flat union of names and a grouped `{ read, write }` object — collapsed to one union by `RepositorySpecNamesOf`; only the flat form gets editor completions, because TypeScript's `fromUnionableLiteralType` handles only `ExpressionWithTypeArguments`, `TypeReference`, `IndexedAccessType` and `UnionType`, and a literal inside a tuple inside a type literal is none of those (measured against the real LanguageService: 15 / 14 / 0 / 2). The per-key contracts (`ICanReadBy`, `ICanReadManyBy`) are mapped types remapping over `Key` itself (``[Each in Key as `findBy${Capitalize<Each>}`]``), **not** over the generated names — with `Key` a union the latter pairs every method with the union of every key's value type, which is the one regression `ican-read-by.spec.ts` exists to catch. `PerKeyRepositoryContractOf` resolves a name back to a key by generating **forward** and index-collapsing (the "map then index-collapse" idiom), never by `Uncapitalize`, whose round-trip breaks outside camelCase (`URL` → `findByURL` → `uRL`). `ICanReadId` is a named alias of `ICanReadBy<E, "id">`, not a ninth contract: identity keys are already in `RepositoryFilterKeysOf` via `keyof IRawEntity`, so `findById` falls out of the same generator. `IEntityReader`/`IEntityWriter`/`IEntityRepository` are likewise defined *through* `RepositoryOf` over their own catalogs rather than by relisting contracts, so they cannot drift. Order carries weight in two places: `RepositoryContractOf` tests `findManyByIds` before falling through to the per-key branch (a blueprint key literally called `ids` loses the name to the batch loader — documented, not engineered around), and `PerKeyRepositoryContractOf` tests `findManyBy…` before `findBy…` (every `findManyByX` also matches `findBy${string}`).
- **`collections/`** — the Schema / Value Object catalog (see below).

**`application/`**
- **`command/`** — the `Command` base (`application/command/command.ts`, also home to `BoundCommand`, `commandOf`'s internal base) and `AggregateCommand` (`application/command/aggregate-command.ts`, also home to `BoundAggregateCommand`, `aggregateCommandOf`'s internal base), plus `helpers/` and `types/`. Structurally the same blueprint-driven construction/validation machine as `Entity`, minus identity (`id`/`createdAt`/`updatedAt`) and mutation (no `set`/`setMany`) — a `Command` is built once, read through typed accessors, and `execute()`d. `AggregateCommand` specializes it for a single-aggregate result: `execute()` comes already implemented, and the subclass writes `handle()` instead. `defineUseCase` (`helpers/define-use-case.ts`) is a friendlier-named alias of `aggregateCommandOf`. See "Command subclass" below.
- **`command-registry/`** — the `commandRegistry(spec).withDependencies(deps)` two-phase builder (`application/command-registry/command-registry.ts`), plus `types/`. Gates `.get(key)` to only the spec keys whose declared `Deps` the `Dependencies` record supplied to `withDependencies` structurally satisfies — resolved entirely at compile time, since `Deps` has no runtime footprint of its own (no symbol slot, unlike `Properties`/`Context`). `.get(key)` returns a bound, ready-to-run function — not the class, not an unexecuted instance — that constructs the command and calls `execute()` on it with the stored `Dependencies`. No `helpers/` subdir: unlike `command/`, this pillar derives no schema and installs no accessors, so the whole implementation fits in `command-registry.ts`. Built entirely from `command/`'s already-public surface (`CommandResult` alone) — see "CommandRegistry usage" below.
- **`evented-registry/`** — `eventedRegistry(spec, emitter, options?).withDependencies(deps)` (`application/evented-registry/evented-registry.ts`), plus `helpers/` and `types/`. `commandRegistry`, gaining event behaviour: every event a registered command's `CommandResult` carries is auto-published through the injected `IEventEmitter`, and reactions registered via `.on(eventClass, handlerClass)` run — `await`ed, isolated — before that call resolves. Delegates command construction/execution entirely to a real `commandRegistry(spec).withDependencies(dependencies)` underneath rather than reimplementing it, building a second, parallel `commands` bag — one instance per point in the call chain, via its own `buildCommands(chain)` (see below), the same recursive-not-flat shape `command-registry.ts` now uses — reachable from both `.get()` and every reaction's `deps.commands` — so a reaction's own command call runs through the same decorated runner, and its events are themselves auto-published/auto-reacted-to. A reaction is a class implementing `IEventHandler<Event, Deps>` (one method, `handle`) — an interface, not an abstract base like `Command`, since there's no blueprint to validate and so nothing to centralize. Matching a raised event against a registered `eventClass` is by `name`, never `instanceof` (`Entity.raiseEvent` spreads the built event into a fresh plain object before buffering it, so the class relationship doesn't survive) — `helpers/name-of.ts` resolves it once, at `.on()` time, off an `Object.create(eventClass.prototype)` probe, the same construction-free pattern `definitionOf`/`read-definition.ts` already uses for a blueprint. `deps.commands` is gated at compile time by `RegistrableEventHandlerClass` (`types/registrable-event-handler-class.type.ts`), a conditional type applied directly to `.on()`'s parameter rather than `RegistrableKeys`'s collapse-a-known-union approach, since `.on()` takes one candidate class at a time with no finite spec to map over first — same one-hop limitation as `SiblingCommands`/`RegistrableKeys`, same reason (no fixpoint proof at arbitrary depth). A throwing reaction is isolated via `helpers/default-on-error.ts`'s microtask re-throw fallback, or the optional `onError` hook — never rejecting the `CommandResult` of the command that raised the event. A reaction chain that cycles back to a command key or event name already on its own call chain (a triggered command raising the same event again, directly or through further reactions) throws `helpers/cycle-error.ts`'s `LoopDetectedException` (HTTP 508) instead of recursing until the stack gives out — the same runtime backstop `command-registry`'s own sibling composition now has; for a cycle closing on an *event* specifically, `react()` routes it through `onError`/`defaultOnError` like any other reaction failure instead of throwing, preserving the "never rejects the `CommandResult`" guarantee above. A reaction needing nothing but its `handle` logic can skip the class entirely via `defineEventHandler(handle, name?)` (`define-event-handler.ts`), the same `(args) => class` idiom `defineDomainEvent`/`defineValueObject` already use — returns a class typed `EventHandlerClassOf<Event, Deps>` (`types/event-handler-class-of.type.ts`), directly usable with `.on()`.
- **`collections/`** — a thin, hand-kept-in-sync alias onto `domain/collections/*` (same classes, re-exported), so a `Command` blueprint never has to import from `domain/` directly. The sync is no longer only by hand: `application/collections/collections-alias.spec.ts` asserts, for all six mirrored subpaths, that the two barrels export the same names (read from the source, so the type-only `custom/types` barrel counts too) **and** that each name resolves to the very same object — a redeclaration in place of a re-export would keep every name lined up while breaking `instanceof`.

**`shared/`**
- **`helpers/`** — the handful of helpers both pillars use verbatim: `installAccessors`, `applyRuleDefaults`, `rulesOf`, `isValueObjectClass` (the structural "has `defineMeta` on its prototype" test, extracted from `redaction/sensitive-keys-of.ts` once `domain/entity/helpers/resolve-unique-keys.ts` needed the identical predicate — the same "two copies only guarantee one gets fixed" reasoning that moved the other three here). **Deliberately has no `index.ts`.** `package.json`'s `exports` uses the `./*` wildcard mapping to `dist/*/index.d.ts`, so *any* barrel becomes a public subpath; without one, this stays genuinely internal while knip still counts the direct-path imports as usage. Put something here only when both pillars need the exact same behaviour — a helper that would need an `if (pillar === …)` belongs to a pillar, not here.
- **`redaction/`** — the sensitive-value machinery: `configureRedaction`/`redactionConfig` (module state, **not** `globalThis`), `sensitiveKeysOf` (per-blueprint memo, `WeakMap`-keyed like `models`), `resolveSensitiveKeys` and `redactIfSensitive`. Also barrel-free, like `helpers/`; the two public functions and their types are re-exported from the **root** barrel instead, since redaction is a package-wide switch rather than a pillar's concern. The asymmetry is the design: `Command.toJSON()` redacts (never persisted; `toJSON` is what a structured logger reaches through `JSON.stringify`), `Entity.toJSON()` does **not** (persistence contract, must round-trip through `fromJSON`) and offers `toSafeJSON()` instead, which recurses so each nested entity applies its own keys. `toString()` and the `nodejs.util.inspect.custom` hook redact on both. Two sources declare *which* keys — `sensitive: true` on a value-object's `defineMeta` (travels with the type) and `sensitive: [...]` on `defineEntity`/`defineCommand` (this aggregate only) — and two declare *how*, the per-class `redactWith` beating the global `placeholder`. Both accept a ready value or a `(value, context)` function; the function receives the real value, which is the whole reason partial masking (`a***@b.dev`) is expressible. Ready-vs-function is discriminated by `typeof`, exactly as `meta.default` does for its thunk form, so a placeholder that is itself a function cannot be expressed.

**`way/`** — `@roastery/beans/way`, one import path for the low-ceremony subset of the two layers above: `blueprint`/`entityOf` (domain modeling), `defineDomainEvent` (events), `defineUseCase` (a single-aggregate `AggregateCommand`, alias of `aggregateCommandOf`), `defineEventHandler`/`eventedRegistry` (reactions/orchestration), plus the `IEventEmitter` and `RepositoryOf` types — `RepositoryOf` being the port generator a `way`-built feature declares its persistence contract with, while the granular `ICan*` capabilities it fuses stay behind `domain/repository/types`, the same escape hatch every other precise form keeps. `src/way/index.ts` contains zero logic — only `export { X } from "..."` lines — the same "hand-kept alias, nothing reimplemented" deal `application/collections/*` already is for `domain/collections/*`. The value-object catalog lives one level deeper, at `way/collections/value-objects` (+ `/optional`, `/nullable`, `/custom`), not in `way/index.ts` itself — flattened in there, its ~45 names would drown the half-dozen that actually shape how a `way`-built feature is put together, the same split `domain`/`application` already draw for their own catalogs. `way/collections/collections-alias.spec.ts` (mirroring `application/collections/collections-alias.spec.ts`) enforces both name parity (read from source) and reference identity at runtime between `way/collections/**` and `domain/collections/**` — `schemas` and `value-objects/custom/types` are deliberately excluded from both the barrel and the spec, since a low-ceremony blueprint only ever needs the VO classes themselves. Every name `way` exports is still reachable from its original subpath too; `way` only adds a shorter path, it removes nothing.

**`testing/`** — `@roastery/beans/testing`, home of `inMemoryRepositoryOf` (`src/testing/in-memory-repository-of.ts`), which generates a working in-memory repository from an entity's blueprint and types it as **the very same `RepositoryOf` port** a real adapter implements — not a parallel test interface to keep in sync, so a double is substitutable by construction. **Not a layer**, like `way/` and `shared/`: `domain` and `application` are still the only two, and this is a *time-of-use* concern. It is, however, the **first runtime in `beans` outside the two layers**, which is exactly why it sits behind its own subpath and is deliberately absent from `way/` (which curates the low-ceremony subset of *production* entry points): a production bundle must not reach it by accident, and the `repository` pillar it doubles stays type-only, with `dist/domain/repository/types/index.js` still literally 0 bytes. Reads the blueprint via `definitionOf` — the same construction-free `Object.create` probe `Entity.fromJSON` and `entityHas` use. Three arguments: the class, an optional spec, an optional handler. **The spec applies at runtime, not only in the type** (`["findById"]` yields an object with exactly one method), and accepts both the array and `{ read, write }` forms — with none of the type level's asymmetry, since a **value** position drives completions from the contextual type: measured against the real LanguageService, both forms offer the full catalog here, where at the type level only the flat union does. An empty or omitted spec means the **whole catalog**, deliberately inverting `RepositoryOf`'s empty-selection-is-`never` rule, because `inMemoryRepositoryOf(User, [], handler)` is how a caller reaches the third argument without narrowing the second. The double's **writes behave like a database, not a `Map`**, and this is the pillar's (and the package's) **first and only consumer of `@roastery/terroir/exceptions/infra`** — fitting, since `testing/` is the one runtime here that plays the role of an adapter. `create` throws `ConflictException` on an already-stored `id` (checked *before* the unique scan, so a primary-key violation is reported by its own name rather than as "duplicate field `id`") or on a taken unique value; `update`/`delete` throw `ResourceNotFoundException` when no row carries the id, because a write affecting zero rows is the "forgot to persist" bug, not an insert. The unique keys come from `uniqueKeysOf(entityClass)`, resolved once at factory time. Three rules in `helpers/unique-conflict-of.ts` come straight from SQL rather than from convenience: a **nullish value never conflicts** (`NULL <> NULL` — the only thing making a unique-but-optional key expressible), comparison goes through `deepEquals` and never `===` (an array-valued VO would never match by reference), and `update` excludes the row it is writing (which is what lets an unchanged unique value through, with no change-tracking needed). The scan reads `rows` directly, **not** any generated `findBy*`: a repository built with `spec: ["create"]` has no readers and must still refuse a duplicate. The double is **faithful, not convenient**: it stores `toJSON()` and rehydrates through `fromJSON` on every read, so mutating after `create` does not persist (only `update()` does) — which catches the "forgot to call update" bug rather than hiding it, at the stated price that `toBe` will not hold and `[Events]`/`[Storage]` come back empty. Filtering goes through `deepEquals`, never `===`: an array-valued VO (`StringArrayVO`/`UuidArrayVO`) serializes to an array that reference equality would never match, silently. The handler receives a **snapshot** of the generated methods plus `rows`/`hydrate`, and its return is merged **over** them — so a colliding name replaces one while still reaching the original through the snapshot, the decorator shape a double needs for "make the third call throw". `helpers/repository-catalog-of.ts` is **the one place in the package where a rule exists twice**, once as `RepositoryReadMethodsOf` and once as a runtime list — unavoidable, since a union type is not enumerable at runtime — and `in-memory-repository-of.spec.ts` carries a dedicated drift guard (`as const satisfies` in one direction, an `Equal` assertion in the other) that is the whole reason the duplication is acceptable. `helpers/` has no `index.ts`, same reasoning as `shared/helpers/`.

The pillar's second export is **`NodeEventEmitterAdapter`** (`src/testing/node-event-emitter-adapter.ts`), Node's `EventEmitter` wrapped to satisfy `IEventEmitter`. It is here for a second reason on top of the first: `src/testing/` is the **only place in the package that imports a Node builtin**, which is what keeps `domain`/`application` runtime-agnostic — so this is not a claim that the adapter is test-only, and an app whose host is Node can publish through it in production. Its `inner` emitter is `public readonly` and defaults to a fresh one, since that is the only way to subscribe (an `IEventEmitter` has no `.on` — `eventedRegistry` runs reactions through its own registry, never through the emitter). It special-cases exactly one name: `"error"` is Node's one reserved channel and emitting it with no listener throws `ERR_UNHANDLED_ERROR`, which — because `eventedRegistry` `await`s `emit` inside the loop publishing a command's events — would reject the `CommandResult` of a command that succeeded. The adapter returns early when nothing is listening on `"error"`, which is behaviour-identical to every other name (a zero-listener emit is already a no-op) and is not a dropped event.

**The slot symbols are not declared here.** `Context`, `Demo`, `Events`, `Meta`, `Properties`, `Rules`, `Source` and `Storage` come from `@roastery/terroir/symbols` — terroir 0.2.0 moved the first six there so the whole ecosystem shares one declaration site, and 0.2.1 added `Events`. Symbol equality is by reference, so re-declaring any of them locally would key a *different* slot: reads return `undefined` and the type-level matches (`Instance extends { [Properties]: infer Shape }`) silently stop resolving. `src/actions/` existed for this and is gone, as are `src/entity/rules.symbol.ts` and `src/events.symbol.ts` — `Rules` and then `Events` were the local holdouts, in turn, and terroir now ships both. `Command` reuses `Context`, `Demo`, `Properties` and `Source` the exact same way `Entity` does (it has no `Events`/`Storage`/`Rules` slots of its own — see "Command subclass") — it introduces no ninth symbol.

`domain/collections/` ships pairs — for each primitive there is a `*.schema.ts` (the TypeBox schema itself) and a `*.value-object.ts`, 12 of each. There is no `*.dto.ts` layer: since terroir dropped the `Schema` wrapper, the schema *is* the runtime value, so DTO and Schema collapsed into one name. `StringVO` is the one VO that intentionally reuses `StringSchema` rather than declaring its own — and `StringSchema` carries **no** `minLength`, so `StringVO` accepts `""`. A property that must not be empty needs a VO whose schema says so; naming it `name` in a blueprint does not. `collections/value-objects/custom/` is the third piece: factories that build a constrained VO class on the fly, for the rules that don't deserve a file of their own.

`domain/collections/value-objects/optional/` is the fourth piece: `Optional<X>VO` for every one of the 12 (`OptionalStringVO`, `OptionalUuidVO`, …), each just `optionalVO(XSchema, { name: "Optional<X>VO" })` — same schema, `undefined` added to the accepted values, demo-mode default `undefined` instead of the required VO's own. `OptionalSlugVO` is the one exception that carries its own `transform`, mirroring `SlugVO`'s `slugify` call (guarded for `undefined`) — `optionalVO` wraps a *schema*, not a VO's `transform` override, so that has to be re-declared explicitly. None of the required VOs' sugar statics (`BooleanVO.truthy/falsy/from`, `DateTimeVO.now`, `UuidVO.generate`) are mirrored here.

`domain/collections/value-objects/nullable/` is the fifth piece, and `optional/`'s mirror image: `Nullable<X>VO` for every one of the 12, each just `nullableVO(XSchema, { name: "Nullable<X>VO" })` — same schema, `null` added to the accepted values, demo-mode default `null`. `NullableSlugVO` re-declares the `transform` the same way `OptionalSlugVO` does, guarded for `null` instead of `undefined`. **The two subpaths are not interchangeable**: `null` never extends `undefined`, so `UndefinedableKeys` never picks up a `Nullable<X>VO`-backed key — the blueprint key stays required, and the caller must pass `null` explicitly (`new Post({ deletedAt: null })`, never `new Post({})`). `optional/` is for "may not have been provided"; `nullable/` is for "provided, and explicitly empty" (the usual shape of a `NULL` database column).

`application/collections/` mirrors every one of `domain/collections/`'s subpaths (`schemas`, `value-objects`, `value-objects/optional`, `value-objects/nullable`, `value-objects/custom`, `value-objects/custom/types`) with a barrel that only re-exports — explicit `export { X } from "@/domain/collections/…"` lines, never `export *`, kept in sync **by hand** with the domain barrel it mirrors. There is no logic here, only convenience: a `Command` blueprint reaches for `EmailVO` the same way an `Entity` blueprint does, without caring which layer's subpath it came in through.

**Code layout conventions.** One thing per file: each type alias in its own `types/<kebab>.type.ts`, each interface in `types/<kebab>.interface.ts`, each helper function in its own `helpers/<kebab>.ts`. Barrels re-export only the public surface — internal types/helpers are imported by direct path (`@/domain/entity/types/raw-value-of.type`, `@/domain/entity/helpers/read-definition`), which knip counts as usage. The construction machinery that references the `Entity` class itself (`isEntityClass`, `isEntity`, `rawOf`, `modelFor` + its `models`/`deriving` caches, `buildProperty`, `buildContext` + `constructing`) **stays inside `domain/entity/entity.ts`** — extracting it would create circular imports. `BoundEntity` is there for the same reason, one step stronger: it `extends Entity`, so it must be *evaluated* after the class exists, and a sibling module throws `ReferenceError: Cannot access 'Entity' before initialization` on some import orders (this actually happened — `BoundEntity` started life in its own file). What does **not** touch the class was extracted: `acceptsUndefined`, `buildBaseContext`, `cycleError`, `modelOfValueObject` and `RAW_ENTITY_KEYS` live in `domain/entity/helpers/` and are imported back by direct path. `application/command/command.ts` does **not** have this constraint: a `Command` blueprint is value-object-only (never a nested `Command` or `Entity`), so nothing in its construction machinery needs to import `Command` itself, and `buildContext`/`modelFor`/`installAccessors` live as ordinary internal helpers under `application/command/helpers/` instead.

Only some of the entity helpers are public: `domain/entity/helpers/index.ts` exports `blueprint`, `entityOf`, `entityHas`, `deepEquals`, `generateUUID` and `uniqueKeysOf`. `resolveUniqueKeys` is **not** among them — it is the internal engine `uniqueKeysOf` and `Entity`'s constructor both call by direct path, the same line that keeps `readDefinition` internal. `extractIdentity` and `readDefinition`/`definitionOf` are internal — `entity.ts` is their only consumer and imports each by direct path. Adding one to the barrel widens the published API, so leave them out unless that is the intent. `application/command/helpers/index.ts` draws the same line, differently shaped: `aggregateCommandOf`, `collectDomainEvents`, `collectResult`, `commandOf` and `defineUseCase` are public; `readDefinition`, `readBoundDefinition`, `modelFor` and `buildContext` are internal to `command.ts`/`aggregate-command.ts`. The three helpers both pillars share — `installAccessors`, `applyRuleDefaults`, `rulesOf` — live in `src/shared/helpers/` instead (see below).

### Subpath exports

`package.json` `exports` uses the `./*` wildcard, so every `src/**/index.ts` becomes its own entry point under `dist/**/index.{js,cjs,d.ts}`. The granular subpaths are part of the public API:

```ts
import { blueprint, Command, DomainEvent, Entity, ValueObject } from "@roastery/beans";
import { AggregateCommand, Command as ApplicationCommand, commandRegistry } from "@roastery/beans/application"; // AggregateCommand isn't in the root barrel
import { Context, Demo, Events, Meta, Properties, Rules, Source, Storage } from "@roastery/terroir/symbols";
import { deepEquals, generateUUID } from "@roastery/beans/domain/entity/helpers";
import type { AccessorsOf, EntityDefinition, IEntity, IRawEntity } from "@roastery/beans/domain/entity/types";
import type { IDomainEvent } from "@roastery/beans/domain/domain-event/types";
```

## Subclass patterns

### ValueObject subclass

`extends ValueObject<TValue, typeof XSchema>` and implement `defineMeta()`. That's the whole class — no constructor, no `super`, no payload wrapper:

```ts
class StringVO extends ValueObject<string, typeof StringSchema> {
	protected defineMeta(): IValueObjectMetadata<string, typeof StringSchema> {
		return { default: "string", schema: StringSchema };
	}
}

new StringVO("alan", { name: "name", source: "bean" });
StringVO.demo({ name: "name", source: "bean" });
```

Override `transform()` when the value needs normalising before validation (e.g. `SlugVO` slugifies). Sugar statics are plain additions (`BooleanVO.truthy/falsy/from`, `DateTimeVO.now`, `UuidVO.generate` — the last two are aliases of `demo`).

- **`defineMeta` must be a prototype method, never a class field** — the base calls `this.defineMeta()` *inside* its constructor (it needs the `schema` to validate), and a class-field initializer only runs after `super()` returns. Guarded at runtime with an `InvalidEntityDefinitionException` that explains the ordering, since TS can't reject a property overriding a method. It must also be **pure**: `metaOf(Class)` invokes it on an `Object.create`d probe with no constructor run. The subclass never touches `[Meta]` itself — the base fills it from `defineMeta()`.
- **`meta.default` must pass `meta.schema`.** The base validates the default like any other value. Since `Entity` derives its schema from the blueprint, a bad default also breaks demo-mode construction of every entity using the class. `SlugSchema` has `minLength: 1`, so `""` is not a valid default for a `SlugVO` — while `StringSchema` constrains nothing beyond the type, which is why the specs reach for a slug whenever they need a value the schema refuses.
- **`meta.default` may be a thunk, and should be whenever it's expensive.** `defineMeta()` runs on every construction, so a computed default would too — including on the constructions that pass a real value and throw the default away. `DateTimeVO` and `UuidVO` declare `default: () => new Date().toISOString()` and `default: generateUUID`; the base only calls it in demo mode. The discriminant is `typeof === "function"`, so a VO that wrapped a *function* value would have to double-wrap it — no VO in the domain does.
- **`meta.unique` is declarative and nothing in the domain enforces it.** `unique: true` says the value must not repeat across the rows of the aggregate holding it — an invariant of the *set*, which neither a `ValueObject` (one value) nor an `Entity` (one aggregate) can see. Construction never fails because of it, and two entities carrying the same unique value are perfectly legal. It is read back by `uniqueKeysOf(EntityClass)` / `Entity#isUnique(key)` and enforced by whoever implements the repository port; `inMemoryRepositoryOf` is the one implementation shipped here. Mirrors `sensitive` exactly, including the second declaration site (`unique: [...]` on `defineEntity`) and the free ride through `IValueObjectHooks` into all eight custom-VO factories. `Command` ignores it — never persisted, no set of rows.
- **`transform` does not run over defaults** — declare them already in canonical form (`SlugVO`'s default is `"slug"`, not something to slugify).

### Entity subclass

Two forms, both supported.

**`entityOf(properties, source)` is the default** — it returns a base class already bound to the blueprint, so the subclass declares only its own behaviour, and the accessors come out typed **without** the declaration merge:

```ts
class Author extends entityOf(authorProperties, "author") {
	public rename(value: string): void {
		this.set("name", value);
		this.raiseEvent(AuthorRenamed); // protected members stay reachable
	}
}
```

It removes the three pieces of ceremony the class form needs — `defineEntity`, the `interface X extends AccessorsOf<…> {}` merge, and that merge's `biome-ignore` — and with them the package's one silent failure mode. `commandOf<Shape, Deps, Result>(properties, source)` is the application-layer twin; `Deps`/`Result` are explicit because no blueprint mentions them. Both take the rest of the definition (currently `sensitive`) as an optional third argument, and both must be **called once at module scope**, like every other class factory here. The lifecycle decorators stack on a factory-built class unchanged.

**The class form below stays correct** and is the one to reach for when a subclass computes its definition rather than stating it. Declare a blueprint (`const xProperties = { field: XVO }`), extend `Entity<typeof xProperties>` and implement `defineEntity()`. The base supplies `id`/`createdAt`/`updatedAt` — they must **not** appear in the blueprint. No constructor is needed: the base's is inherited.

```ts
const xProperties = { field: FieldVO, owner: OwnerEntity };

// biome-ignore lint/correctness/noUnusedVariables: merging with the class below is the use.
interface X extends AccessorsOf<typeof xProperties> {}
class X extends Entity<typeof xProperties> {
	protected defineEntity(): EntityDefinition<typeof xProperties> {
		return { properties: xProperties, source: "x" };
	}
}

new X({ field: "value", owner: { name: "alan" } }); // fresh identity
X.demo();                                           // demo mode
X.fromJSON(row);                                    // strict hydration

x.field;      // typed accessor
x.owner.name; // chains — the accessor returns the nested instance
x.id;         // getter from the base
```

- **`defineEntity` must be a prototype method, never a class field.** Same trap as `defineMeta`: the base calls `this.defineEntity()` *inside* its constructor, and a class-field initializer only runs after `super()` returns. Guarded at runtime with `InvalidEntityDefinitionException`. It must also be **pure** — `fromJSON` invokes it on an `Object.create`d probe with no constructor run, purely to read the blueprint before validating.
- **A subclass may still declare its own constructor** and delegate to `super(...)`; it must accept the base's context payload — as one of its overloads is enough — and forward to `super` any argument it doesn't recognise, because `demo()` passes a module-private sentinel through that same channel. See `Tag` in `entity.spec.ts`.
- **`X.demo()` is the entry point without data** — a static, like `fromJSON`. Each VO falls back to its `[Meta].default` and nested entities recurse into their own demo mode.

**Accessors.** Every blueprint key is readable as a plain property, and `id`/`createdAt`/`updatedAt` are concrete getters on the base.

- **The `interface X extends AccessorsOf<…> {}` line is what types them.** The getters are installed at runtime regardless (on the *prototype*, derived from the blueprint, once per class); the interface merge is how TS learns about them. Skip the line and the accessors still work but stay invisible to the type system — so don't skip it. `AccessorsOf` mirrors `get`, so an entity-valued key yields the nested **instance**. This is the **one silent failure mode** left: everything else fails loudly with an exception naming the cause.
- Read-only. `set`/`setMany` remain the only mutation path, which is what keeps the `updatedAt` stamp explicit.
- **A blueprint key may not collide with an existing member** (`schema`, `toJSON`, `get`, `set`, `id`, …). The base checks `key in prototype` before defining anything and throws `PropertyNameCollisionException` carrying the key in its `property` slot; the install is atomic, so a rejected attempt leaves the prototype untouched and the next attempt throws again. (`name` is safe — it lives on the constructor, not the prototype.)
- **Subclassing a concrete entity works.** The install walks the prototype chain, collects the keys an ancestor already covers and defines only the missing ones — so a subclass that overrides `defineEntity` with a *wider* blueprint still gets accessors for its new keys, and the collision guard doesn't fire against the ancestor's own accessors.
- `noUnsafeDeclarationMerging` is **off** in `biome.json` because of this pattern — the merge is deliberate here, not accidental. `noUnusedVariables` still fires on each interface (it doesn't count the merge as a use), so each declaration carries a one-line `biome-ignore`.
- **Identity is optional in the payload, all-or-nothing.** `RawContextOf` intersects the blueprint's raw values with a two-variant union: either none of `id`/`createdAt`/`updatedAt` appears (the base stamps a fresh identity via `UuidVO.generate` / `DateTimeVO.now`, in `buildBaseContext`), or `id` **and** `createdAt` come together, with `updatedAt` still optional. Half a payload is a compile error, and `extractIdentity` (in `domain/entity/helpers`) mirrors that guard at runtime for plain-JS callers, throwing `IncompleteIdentityException`. That class has no `property` slot — the identity is one unit, and it is the whole unit that is incomplete — so the missing key survives only in the message.
- **Two hydration paths, and they differ.** `new X({ ...row })` validates VO by VO and ignores keys outside the blueprint. **`X.fromJSON(row)` is static** — it validates the whole payload against the aggregate schema first, rejecting missing **and extra** keys with `InvalidDomainDataException`, and needs no throwaway instance. Use it for payloads of untrusted origin. Both preserve the payload's identity.
- **Class fields on the subclass are fine.** `fromJSON` and `demo` build through `Reflect.construct`, which runs the subclass constructor and therefore its field initializers, so all three construction paths produce the same shape. Two consequences: the subclass **constructor body also runs** on hydration and in demo mode (side effects included), and domain state still belongs in the blueprint, transient state in `[Storage]`.
- **`[Storage]` is the sanctioned escape hatch for transient state** — the `EntityStorage` class, a per-instance `string → string` store for cached lookups and derived flags. It is `protected`, so a subclass exposes whatever facade it wants; the `Storage` symbol comes from `@roastery/terroir/symbols`. It is initialised in all three construction paths and **starts empty on `fromJSON` / `demo`** — those are statics with no source instance, so there is nothing to carry over. It never reaches `toJSON` or `schema`, and it cannot collide with an accessor (those only take string keys).
- **`raiseEvent`/`pullDomainEvents` are the domain-event buffer**, backed by the `[Events]` slot (per-instance `IDomainEvent[]`, `protected` like `[Storage]`, initialised the same way and **starts empty on `fromJSON`/`demo`**). `raiseEvent` is `protected` — a subclass calls it from its own business methods, never automatically from `set`/`setMany`. It stamps `occurredAt`/`aggregateId` itself and does not accept them from the caller, so an event can never misreport which entity (or when) it came from; `beans` is not event-sourced, so there is no replay path that would need to override either. Prefer raising from the aggregate root — an event raised inside a nested entity lands in that entity's own buffer, and `pullDomainEvents` (`public`) is **shallow by default**: it drains only `this[Events]`, unlike `toJSON`, which always recurses. `pullDomainEvents({ deep: true })` opts into the recursion, walking `[Context]` for `isEntity` values and concatenating root-first; that is the form to use whenever a nested entity carries lifecycle decorators, since `onCreate` then fires on every construction of the parent and a shallow pull would strand it. `beans` ships no dispatcher: `pullDomainEvents` only drains the buffer (`Array.prototype.splice(0)`), what happens with the result is the consuming application's call — the `application/command` pillar's `collectDomainEvents` helper is the sanctioned way to gather that result across one or more aggregates and hand it to a `Command`'s caller. `raiseEvent`'s parameter type is `Event | (new (aggregateId: string) => Event)` — a payload-less `DomainEvent` subclass (one that doesn't override the inherited `constructor(aggregateId: string)`) can be passed **bare, as the class itself**, and `raiseEvent` does `new event(this.id)` when `typeof event === "function"`. A subclass whose constructor needs more than `aggregateId` (an overridden constructor with extra required params) is not assignable to `new (aggregateId: string) => Event`, so TypeScript routes it to the "already built" branch instead and rejects the bare-class form at compile time — no runtime check needed to enforce that, the constructor signature itself is the guard.
- **`DomainEvent` (`domain/domain-event/domain-event.ts`, its own pillar) is optional sugar over `IDomainEvent`, not a second contract.** A subclass declares only `defineName()` and passes `aggregateId` through `super()`; the base stamps `occurredAt` itself. It follows the exact `defineMeta`/`defineEntity` shape: `defineName` **must be a prototype method, never a class field** (same `InvalidEntityDefinitionException` guard, checked inline in the constructor rather than through a dedicated `read-*` helper, since nothing else needs to probe it without constructing). Because `raiseEvent` always overwrites `occurredAt`/`aggregateId` on the way into the buffer regardless of what the passed object already carries, a `DomainEvent` instance and a plain `{ name, ...payload }` object behave identically there — reach for `DomainEvent` when an event has payload fields of its own and a class reads better than the literal, not because `raiseEvent` requires it. `entity.ts` imports `IDomainEvent` cross-pillar, via `@/domain/domain-event/types` — the first (and so far only) place the `@/*` alias crosses from `entity/` into a sibling pillar *within* `domain/` (the `application/command` pillar crossing into `domain/` for `IDomainEvent` too, in `CommandResult`, is the second — but that crossing is expected: `application` depends on `domain`, never the reverse).
- **`defineDomainEvent(name)` builds a payload-less `DomainEvent` class from just its name** — the same "factory returns a class, not an instance" idiom `domain/collections/value-objects/custom` already uses for `ValueObject`. It exists for the common case a hand-written subclass is pure boilerplate for: an event with no fields beyond what `DomainEvent` already stamps (`name`/`occurredAt`/`aggregateId`), the exact shape `raiseEvent`'s bare-class form (see above) accepts without `new`. Its return type is annotated `DomainEventClassOf` (`domain/domain-event/types/domain-event-class-of.type.ts`) for the same reason `ValueObjectClassOf` exists on the custom-VO factories: the class is declared *inside* the function body, so an inferred return type fails the declaration build with **TS4060**. `DomainEventClassOf` takes no type parameters — `DomainEvent` isn't generic — and its shape (`new (aggregateId: string): DomainEvent`) is structurally compatible with both `Entity.raiseEvent`'s inline bare-class type and `BareDomainEventClass` (`domain/entity/decorators/types`) without importing either: the same "discriminate structurally, not by `instanceof` across pillars" preference the rest of the package already follows. Scope is deliberately payload-less only — an event with fields of its own still needs a hand-written subclass, since a constructor with extra required parameters isn't something a `(name: string) => Class` factory can produce. Like every custom-VO factory, **call it at module scope, once**: each call mints a fresh class, so two calls with the same name produce classes `instanceof` does not relate. The generated class's `.name` is set to match the given name via the same two-line `Object.defineProperty` trick `defineValueObject` and the lifecycle decorators' `renameDecorated` already use — copied inline here rather than imported, since `renameDecorated` lives in `domain/entity/decorators/helpers/`, a different pillar, and reaching into it would be the first dependency from `domain-event/` back into `entity/`.
- **The schema belongs to the blueprint, not the instance.** It's derived from the property classes and memoized in a module-level `WeakMap` keyed by the blueprint object, so every instance of a class shares one `t.TObject`. Every level is emitted with `additionalProperties: false`. Keeping that model stable is also what keeps validation cheap: `SchemaManager.match` caches the compiled validator against the schema's *object identity*, so the model is compiled once per blueprint rather than once per call.
- **`setMany` is the mutation primitive; `set` delegates to it.** It validates every key, then builds every value, and only then assigns — so a rejected value leaves the entity untouched. `updatedAt` is stamped **once** (via `DateTimeVO.now`), and only if something actually changed.
- **`get` and `set` reject unknown keys** with `InvalidPropertyException` (the check is `Object.hasOwn`, not `in`, so `Object.prototype` keys don't leak in). `get("updatedAt")` on an unmutated entity still returns `undefined` — a known key with no value is a different case from an unknown key.
- **Writing to `id`/`createdAt`/`updatedAt` is a different failure from writing to an unknown key**, and `setMany` says so: identity fields raise `ImmutablePropertyException` (they are readable, never writable), unknown keys raise `InvalidPropertyException`. `get` accepts the identity fields, so it only ever raises the latter.
- **`isUnique(key)` reports the declaration, never the stored data — and it must stay that way.** It answers "was this field declared unique?", resolved once per instance into a `#unique` slot from `id` + each value-object's `meta.unique` + the definition's own `unique: [...]` list, exactly as `#sensitive` is resolved. It is **not** async and must not become async: "is this value already taken?" is a question about the set of rows, which an instance cannot see, and making the method reach for storage would put an I/O call inside the domain layer. `id` always returns `true` (primary key); `createdAt`/`updatedAt` always `false`. An unknown key throws `InvalidPropertyException` rather than answering `false`, reusing `get`'s guard verbatim — a typo reading as "not unique" is the silent failure the package avoids everywhere else. `uniqueKeysOf(EntityClass)` (`domain/entity/helpers`, public) is the same declaration read off the class, for an adapter with no instance yet. **The always-`id` guarantee lives in `helpers/resolve-unique-keys.ts`, not in `entityOf`** — seeding it in the factory would make the factory form and the hand-written `defineEntity` form disagree, and the two are kept equivalent on purpose; `entity-of.ts` has no line about uniqueness at all.
- **`destroy()`/`isDestroyed` are a lightweight marker, not a hard guard.** `destroy()` flips a true JS private field (`#destroyed`, not a terroir symbol slot — nothing outside the class needs to key off it) and calls `this[Storage].clear()` (a new `EntityStorage` method, mutating its `private readonly items` in place). Idempotent — a second call is a no-op, which is what lets `onDelete` (below) tell a real destruction from a repeated one by checking `isDestroyed` *before* delegating to `super.destroy()`. There is no way to force garbage collection from inside the entity itself, so this does **not** guard `get`/`set`/`toJSON`/etc. afterwards — "removed from memory" here means the transient cache is released and the fact is recorded, nothing more.

**Blueprint rules.** `blueprint(shape).with(rules)` (in `domain/entity/helpers/blueprint.ts`) attaches per-property domain rules — `{ default }` (a fallback belonging to the entity, outranking the VO's own) or `{ derive }` (computed from siblings). The two are mutually exclusive.

```ts
const postTagProperties = blueprint({ name: TagName, slug: TagSlug, hidden: TagVisibility })
	.with({ slug: { derive: (raw) => raw.name }, hidden: { default: false } });

new PostTag({ name: "Alan Reis" }); // slug: "alan-reis", hidden: false
```

- **The rules live under the `Rules` symbol key on the blueprint object itself** (from `@roastery/terroir/symbols`; `rulesOf` reads the slot, `blueprint().with()` writes it). That is what makes the feature cheap: `Object.keys`/`Object.entries` skip symbols, so `modelFor`, `installAccessors`, `toJSON` and every other traversal keep seeing exactly the domain properties. The type-level counterpart is `DomainKeys<Shape>` (`Extract<keyof Shape, string>`) — **every mapped type over a blueprint must go through it**, or the slot leaks as an accessor/schema field/serialized key. Six already do (`AccessorsOf`, `ContextOf`, `EntitySchemaOf`, `InputValuesOf`, `SerializedValuesOf`, `ReadableKey`) — `application/command` carries its own parallel `CommandDomainKeys`, since `Command`'s blueprint is a different (narrower, value-object-only) shape.
- **Ruled keys are optional in the constructor payload** (`ConstructionValuesOf` inside `RawContextOf`). For a plain blueprint `RuledKeys` is `never`, so everything collapses to the previous behaviour. `application/command`'s `RawCommandContextOf` applies the exact same resolution, minus the identity intersection `RawContextOf` needs.
- **So are `undefined`-accepting keys**, through the same `ConstructionValuesOf`, via `UndefinedableKeys` (`domain/entity/types/undefinedable-keys.type.ts`): any key whose VO class's `value` type includes `undefined` (built with `optionalVO`, or one of the `Optional*VO` catalog classes). No rule is required — the runtime already read a missing key the same as an explicit `undefined` (`buildContext` indexes `raw[key]`), so this is purely a type-level catch-up, not a behaviour change. `UndefinedableKeys` reads `["prototype"]["value"]` directly rather than going through `InputValueOf`, deliberately skipping the nested-entity branch: recursing through `InputValueOf` there would re-enter this same type for a self-referencing blueprint (`{ child: Node }`) and TypeScript rejects that as a circular mapped type. `null` (from `nullableVO`/`Nullable*VO`) is **not** picked up by this — `null` never extends `undefined`, so a nullable key stays required; only `undefined`-accepting keys become omittable.
- **Resolution is explicit value > `default` > `derive`**, all inside `buildContext`: `applyRuleDefaults` fills the `default` rules over the payload first, the main loop builds every non-derived key, then a second pass resolves the derivations. They run in **blueprint order** and read siblings already built and normalised (a `SlugVO` sibling reads back slugified). A derivation reading a key derived later gets `undefined` and fails on that property's validation.
- **"Omitted" means `undefined`, not falsy.** `applyRuleDefaults` tests `values[key] !== undefined`, so an explicit `false` or `0` or `""` counts as a supplied value and the rule's `default` does not fire — which is exactly what a `{ hidden: { default: false } }` rule needs in order to be overridable with `true`.
- **Rules apply in `demo()`** — that is what makes fixtures coherent instead of a bag of unrelated defaults. Keys with no rule still go through the VO's `.demo()`, so `transform` still never runs over a VO default.
- **Rules never re-fire on `set`/`setMany`.** Mutation takes explicit values; `tag.set("name", …)` leaves a derived `slug` alone. `Command` has no `set`/`setMany` at all, so this concern doesn't arise there — rules only ever resolve once, at construction.
- **The schema and `fromJSON` are untouched** — rules act on input only, `toJSON()` always emits every property, so every key stays required and hydration stays strict.
- Two phases because a literal cannot reference its own `typeof`; `blueprint(shape)` alone returns **only** the builder, so forgetting to close it is a type error rather than a `with` key leaking into the properties. **A rule-less blueprint closes with `.done()`**, which returns the shape *as given* — same object reference, no `Rules` slot attached, since `rulesOf` already reads a missing slot as empty. It is therefore indistinguishable from the bare object literal; it exists so every blueprint can be spelled the same way instead of some starting with the helper and others with a literal. Do not write `.with({})` — an empty rule map reads like one that was left unfinished.
- **Nesting keeps the rules, at every depth.** A nested entity's payload accepts the same omissions its own blueprint allows (`InputValueOf` → `NestedEntityInput`), and `NestedEntityInput` is just `ConstructionValuesOf<Shape>` — the *same* type the top level uses. That sameness is the point: the two reach each other (`ConstructionValuesOf` → `InputValueOf` → `NestedEntityInput`), so the relaxation recurses for free and "a complete payload" means one thing at every level. It previously derived from `Omit<ReturnType<toJSON>, keyof IRawEntity>`, which stripped the identity only at the outermost level — a *grandchild* then still demanded its `id`/`createdAt` **and** its ruled keys, so a three-level aggregate (or `set` on a nested entity that itself holds one) could not be written without a cast. The blueprint is still read through an inline `infer` rather than `PropertiesOfClass`: that keeps the mutual recursion lazy, extracting the shape only once a concrete class is substituted instead of eagerly on the widened `AnyEntityClass` bound. `UndefinedableKeys` not going through `InputValueOf` (see above) is the other half of what keeps a self-referencing blueprint from becoming a circular mapped type.
- **Domain vocabulary is free by subclassing a VO**: `class TagName extends StringVO {}` inherits `defineMeta`, `transform`, `demo` and the `instanceof` — including, note, the parent's *lack* of constraints. Override `defineMeta` when the alias needs a stricter schema.
- **`blueprint()`/`RulesOf`/`PropertyRule`/`RuledBlueprint`/`BlueprintBuilder` are reused as-is by `application/command`**, imported straight from `@/domain/entity`/`@/domain/entity/types` rather than reimplemented — they're already public, and generic enough (`PropertiesShape extends PropertiesShapeBase`) that a value-object-only `Command` blueprint satisfies the constraint without modification. See "Command subclass" for what *isn't* reused this way.

### Lifecycle decorators

`domain/entity/decorators/` ships three **standard (TC39 Stage 3) class decorators** — `onCreate`, `onUpdate`, `onDelete` — each declaring which event a point of the lifecycle raises automatically, so a subclass stops calling `this.raiseEvent(...)` by hand at that point. Not `experimentalDecorators`: `tsconfig.json` doesn't set that flag, and the installed TypeScript (5.9.3) supports the standard form natively, which is what the mixin machinery below is built against.

```ts
@onCreate(UserCreated)
@onUpdate(UserUpdated)
@onDelete(UserDeleted)
class User extends Entity<typeof userProperties> {
	protected defineEntity(): EntityDefinition<typeof userProperties> {
		return { properties: userProperties, source: "user" };
	}
}
```

- **`onCreate` wraps the constructor**, calls it through via `super(...args)`, then runs the *same* `extractIdentity` (`../helpers/extract-identity`) the base constructor itself already ran on that argument, firing only when it returns `undefined` (a fresh payload). Calling `extractIdentity` a second time here is redundant but safe: if the identity were malformed, `Entity`'s own constructor would already have thrown `IncompleteIdentityException` before `super(...args)` ever returned. `.demo()` needs no special case — destructuring `id`/`createdAt`/`updatedAt` off the `Demo` symbol yields `undefined` for all three in plain JS, so it falls into the same "no identity" branch a fresh payload does and fires `onCreate`. The logic lives inline in `on-create.decorator.ts`: it used to sit in a shared `construction-lifecycle-decorator.ts` parameterised by a `fireWhenFresh` flag, which existed solely to serve `onRead` as well; with one consumer left, the indirection went away with it.
- **There is deliberately no `onRead`/`onHydrate`.** Rebuilding an entity from storage changes nothing, so it is not a domain fact — and since a repository hydrates through `fromJSON`, an event raised there would ride along in every `CommandResult`: a command that merely loads an aggregate in order to delete it would surface a spurious "read" next to the real event. Audit reads in the repository, where the read actually happens. Do not reintroduce one.
- **`onUpdate` wraps `setMany` only** — `set` already delegates to `this.setMany(...)`, and JS method dispatch resolves that through the real prototype chain, so overriding `setMany` alone catches both. It fires only when something actually changed, read off **`setMany`'s own `boolean` return** — the flag it already computes to decide the `updatedAt` stamp. Comparing `updatedAt` before/after looks equivalent and is not: the stamp is an ISO string with millisecond resolution, so two genuinely distinct mutations landing in the same millisecond would compare equal and the second event would be swallowed. Each decorator also copies the decorated class's `name` onto its wrapper (`decorators/helpers/rename-decorated.ts`), so `User.name` stays `"User"` instead of `"Decorated"` — nothing in `src/` reads `Class.name`, but consumers' stack traces and DI containers do.
- **`onDelete` wraps `destroy()`**, checking `isDestroyed` *before* delegating to `super.destroy()` so a repeated call (already a no-op on the base) doesn't raise the event twice either.
- **Each decorator's event argument is the *bare-class* form only** (`new (aggregateId: string) => IDomainEvent`, aliased as `BareDomainEventClass`) — never a pre-built instance. A decorator is declared once, at the class, with no per-call payload to build a concrete instance from; this is exactly the subset `Entity.raiseEvent` already accepts without `new`.
- **The mixin trap: `EntityConstructor` cannot be `abstract new (...args: any[]) => Entity<PropertiesShapeBase>`.** That looks like the obvious base type, but `Entity<Shape>`'s `toJSON()`/`get()` return types are shape-dependent in a way that makes a concrete `Entity<SomeShape>`'s construct signature structurally incompatible with `Entity<PropertiesShapeBase>`'s (the aggregate `SerializedEntity<PropertiesShapeBase>` needs a string index signature a concrete blueprint's serialized shape doesn't have) — pinning the mixin base there makes every decorated subclass fail to type-check against its own blueprint. `EntityConstructor` instead targets a narrow, blueprint-independent structural slice (`EntityLike`: `[Source]`, `updatedAt`, `isDestroyed`, `setMany`, `destroy` — exactly what the decorators touch), sidestepping the incompatibility entirely.
- **Two more TS mixin-pattern requirements, both load-bearing, not stylistic choices**: the base constructor type's rest parameter must be exactly `any[]` (TS2545 otherwise — `never[]`, the usual "widest signature" trick, does not satisfy this specific check), each carrying a `biome-ignore lint/suspicious/noExplicitAny`; and the generated wrapper class (`class Decorated extends target`) must be declared `abstract` (TS2515 otherwise — the compiler can't see through the generic constructor type that `target` already implements `defineEntity`), even though `Decorated` is never constructed directly and is always cast away (`as unknown as typeof target`) before returning.
- **Reaching `raiseEvent` (protected) from the generated wrapper needs a cast** (`(this as unknown as { raiseEvent(event: unknown): void }).raiseEvent(event)`) — TypeScript's protected-access rules don't resolve reliably through a generic mixin parameter. The same pragmatic-cast spirit `entity.ts` itself already uses in `buildProperty`/`readDefinition`.
- **Stacking all three works without coordination**: each decorator only overrides its own method (constructor, `setMany`, or `destroy`) and delegates the rest via `super`, so the order they're stacked in doesn't matter for correctness (TC39 applies them bottom-up, each wrapping the previous).

### Method decorators

`domain/entity/decorators/` also ships three standard (TC39 Stage 3) **method** decorators — `beforeHandle`, `afterHandle`, `onError` — that raise a declared event immediately before or immediately after an *arbitrary* `Entity` instance method runs, or when it throws, rather than one of the three fixed lifecycle points above. A genuinely different TC39 shape, not a variation on the class decorators: a method decorator receives `(target, context)` where `target` is the method function itself and `context` is a `ClassMethodDecoratorContext`, and returns a replacement function with the same signature — there is no `class Decorated extends target`, no mixin, and none of the TS2515/TS2545 traps that shape requires.

```ts
class Order extends Entity<typeof orderProperties> {
	protected defineEntity(): EntityDefinition<typeof orderProperties> {
		return { properties: orderProperties, source: "order" };
	}

	@beforeHandle(OrderShippingStarted)
	@afterHandle(OrderShippingCompleted)
	public ship(): void {
		// business logic
	}
}
```

- **`EntityMethodDecorator` (internal, `decorators/types/entity-method-decorator.type.ts`) needs three type parameters — `<This, Args extends unknown[], Return>` — where `EntityLifecycleDecorator` needed only one (`Class`).** A class decorator's mixin base collapses to a single constructor type; a method's receiver, argument tuple and return type vary independently per decorated method, so each needs its own generic slot. `Args extends unknown[]`, not `any[]`: with no mixin base class here, none of the TS2545/TS2515 traps apply, so `unknown[]` is strictly safer and needs no `biome-ignore`. Not re-exported from `decorators/types/index.ts`, same internal status as `EntityConstructor`/`EntityLifecycleDecorator`.
- **`beforeHandle`/`afterHandle` are built by one shared helper, `methodHandleDecorator(event, runBefore)`** (`decorators/helpers/method-handle-decorator.ts`) — each is a one-line call into it with `runBefore` flipped. This is the same bar the codebase already enforces elsewhere in this directory: `onCreate` used to share `construction-lifecycle-decorator.ts` with `onRead`, keyed off a `fireWhenFresh` flag, and that indirection was removed the moment `onRead` was deleted and only one consumer remained (see "Lifecycle decorators" above). `beforeHandle`/`afterHandle` have exactly two genuinely parallel consumers — same target, same replacement shape, differing only in which side of one call the raise sits on — so the shared helper is earned by the same rule, not a leftover pattern. `onError` (below) does **not** join this helper — its control flow (`try`/`catch` plus a factory call) isn't a third variation on the same bracket shape, so sharing it would trade duplication for indirection with nothing gained, the same reasoning that keeps `readDefinition` duplicated per pillar.
- **The replacement must be written as `const replacement: typeof target = function (...) {...}` — the function as the *direct initializer* of a `const` typed against `typeof target`.** That is what gives the implicit `this` parameter and the rest parameter `args` contextual typing, inherited from `typeof target`'s own `This`/`Args`/`Return`. A `function replacement(...) {}` declared separately and returned afterwards does **not** get contextual typing — that only applies at a syntactic position that already expects a type (an assignment or return expression), not a later reference to an already-declared, unannotated function — and falls back to implicit `any` under this package's `strict: true`. A hand-annotated alternative such as `function (this: unknown, ...args: unknown[]): unknown` fails differently: return-position assignability is covariant, and `unknown` is not assignable to an arbitrary generic `Return`, only to a `Return` that happens to be `unknown` itself.
- **`target.apply(this, args)`, never a bare `target(...args)` call.** `target` is a detached function value with no receiver of its own; a direct call would run with `this === undefined` in strict mode, breaking any `this.get(...)`/`this.set(...)` the wrapped method's body makes.
- **`renameDecorated` is reused unchanged**, called as `renameDecorated(replacement, { name: String(context.name) })` — `ClassMethodDecoratorContext.name` is `string | symbol`, and `String(...)` satisfies `renameDecorated`'s `{ readonly name: string }` parameter either way. Unlike the class decorators' return (`renameDecorated(Decorated, target) as unknown as typeof target`), no `as unknown as typeof target` cast is needed here: `replacement`'s declared type is already exactly `typeof target`, not a structurally different mixin subclass type.
- **Reaching `raiseEvent` (protected) needs the same inline cast the class decorators use** — `(this as unknown as { raiseEvent(event: unknown): void }).raiseEvent(event)` — since a method decorator's `This` type parameter has no way to be constrained to "has a protected `raiseEvent`" (a protected member can't appear in a structural constraint checked against an unrelated type). No dedicated named type exists for this cast shape; it stays inline, matching how the class decorators already do it.
- **`afterHandle` never fires if the wrapped method throws.** There is no `try`/`catch`: if `target.apply(this, args)` throws, the `raiseEvent` call written after it simply never executes and the exception propagates untouched. This needs no special handling to guarantee — it falls out of ordinary control flow, the same "don't add handling for a scenario that can't happen" reasoning the rest of the package follows, since the scenario here ("the event fires despite the throw") is one this code structurally cannot produce.
- **Neither decorator awaits a `Promise`.** If the decorated method is `async` (or otherwise returns a `Promise`), `afterHandle` raises as soon as the synchronous call returns — once the pending `Promise` itself comes back, not once it settles. No `Entity` method in this package is `async` today, so this is a documented restriction, not an observed gap.
- **Instance methods only, not enforced at runtime.** Decorating a `static` method compiles — nothing in `EntityMethodDecorator` constrains `This` to an instance — but fails at the `raiseEvent` cast at call time, since a static method's `this` is the class constructor, which has no `raiseEvent`. Same spirit as the class decorators: no runtime guard against a use outside the stated contract.
- **Stacking `beforeHandle` and `afterHandle` on the same method always raises before → method → after, regardless of declaration order.** TC39 method decorators apply bottom-up (the one closest to the method wraps first), but each decorator's raise always brackets whatever it wraps — `beforeHandle` fires before delegating, `afterHandle` fires after whatever it wraps returns, including another decorator's own wrapper underneath it. Tracing both orderings confirms the same sequence either way; this mirrors the existing "stacking all three works without coordination" guarantee for the class decorators, extended to a mixed class/method stack.
- **`onError` is the one method decorator in this pillar that catches.** `beforeHandle`/`afterHandle` never introduce a `try`/`catch` — `onError` (`on-error.decorator.ts`) does, wrapping `target.apply(this, args)` in one, calling an `eventFactory(error)` in the `catch`, `raiseEvent`ing what it returns, then **always re-throwing** the original error. The decorated method's observable behaviour is unchanged for its caller; the event is a side channel only, never a way to swallow a failure.
- **`onError` accepts either a `BareDomainEventClass` or a factory, `EntityErrorEventFactory = (error: unknown) => IDomainEvent`.** The factory exists because the other four decorators are declared once, at the class or method, with no per-call payload available — so a bare class (`new event(this.id)`) is the only shape that makes sense for them, while `onError`'s error is genuinely call-time data, and discarding it into a payload-less event would make the decorator far less useful for the cases that want it. But not every `onError` use needs the error's payload, so the bare-class form is accepted too, purely for reading the same way `onCreate`/`onUpdate`/`onDelete` do: `@onError(SomeEvent)` builds a fresh `SomeEvent` on every throw, ignoring the error, the same as `fromClass(SomeEvent)` would. Since `Entity.raiseEvent` always overwrites `occurredAt`/`aggregateId` on the way into the buffer regardless of what either form builds, a factory is free to spend its constructor arguments entirely on the event's own payload (e.g. a `reason: string` derived from the error) and pass any placeholder for `aggregateId`. New type: `EntityErrorEventFactory`, re-exported from `decorators/types` alongside `BareDomainEventClass` (unlike `EntityMethodDecorator`/`EntityConstructor`, it needs to be public since it appears in `onError`'s own public parameter type).
- **The two accepted forms are told apart by `decorators/helpers/is-bare-event-class.ts`, not `typeof`.** `raiseEvent`'s own dual-mode param works by `typeof event === "function"` because its two candidates are an already-*built* object versus a bare *class* — genuinely different runtime types. `onError`'s two candidates are both plain functions (a class reference and a factory both have `typeof === "function"`), so that trick doesn't apply. `isBareEventClass` instead reads the own property descriptor of `prototype`: an ES2015 `class`'s `prototype` is spec-mandated non-writable (ECMA-262 §15.7.14); an ordinary `function` factory's is writable; an arrow-function factory has no own `prototype` at all. All three collapse to one signal — `writable === false` means "a class" — verified directly against the runtime (Bun/JavaScriptCore) rather than assumed, since it is the one place in the package that leans on a JS engine internal instead of a purely structural, duck-typed check. `onError` normalizes a detected bare class through `fromClass` (`decorators/helpers/from-class.ts`, also re-exported publicly) before dispatching — the same `() => new event("")` construction, exposed on its own for whenever that factory value is needed detached from the decorator call.
- **`onError` composes with `beforeHandle`/`afterHandle` the same bracket-nesting way any two method decorators do**: whichever is closer to the method wraps innermost. Stacked with `onError` innermost under `beforeHandle`/`afterHandle`, a thrown error still raises `beforeHandle`'s event (already fired before the call), then `onError`'s event (from its `catch`), then propagates through `afterHandle`'s wrapper without ever reaching its post-call raise — the same "never fires on a throw" behaviour `afterHandle` already has on its own, undisturbed by `onError` sitting underneath it.
- **This is a different `onError` than `eventedRegistry`'s.** `application/evented-registry`'s `onError` hook isolates a throwing event *reaction* by swallowing it (see its own pillar description above). This one wraps an `Entity` business method and never swallows — it always re-throws. Same name, different layer, different contract; there is no ambiguity in the module graph since each lives behind its own subpath.

### Command subclass

Declare a blueprint of **value-objects only** (`const xProperties = { field: FieldVO }` — never a nested `Entity` or `Command`), extend `Command<typeof xProperties, Deps, Result>` and implement `defineCommand()` and `execute()`. No identity, no `set`/`setMany`: a `Command` is built once and read through typed accessors, then `execute()`d with whatever dependencies its behaviour needs.

```ts
const xProperties = { field: FieldVO };

// biome-ignore lint/correctness/noUnusedVariables: merging with the class below is the use.
interface X extends CommandAccessorsOf<typeof xProperties> {}
class X extends Command<typeof xProperties, Deps, Result> {
	protected defineCommand(): CommandDefinition<typeof xProperties> {
		return { properties: xProperties, source: "x" };
	}

	public async execute(deps: Deps): Promise<CommandResult<Result>> {
		// … orchestrate domain behaviour, return { result, events }
	}
}

new X({ field: "value" }); // validates immediately, synchronously
X.demo();                  // demo mode
X.fromJSON(row);            // strict hydration
await new X({ field: "value" }).execute(deps);

x.field; // typed accessor — never a nested instance, the blueprint is VO-only
```

- **`defineCommand` must be a prototype method, never a class field.** Identical trap and identical guard (`InvalidEntityDefinitionException`) to `defineEntity`/`defineMeta`/`defineName` — the base calls it *inside* the constructor, and it must be pure (`fromJSON` probes it via `Object.create`, no constructor run).
- **The blueprint may only hold `ValueObject` classes** — `CommandPropertiesShapeBase = Record<string, AnyValueObjectClass>`, narrower than `Entity`'s `PropertiesShapeBase` (which also accepts a nested `Entity`). A `Command`'s input is a flat, validated payload, not an aggregate. One consequence: there is **no cycle to guard against** — `application/command`'s `modelFor`/`buildContext` carry no `deriving`/`constructing` guards or `CyclicEntityDefinitionException`, because a value-object-only blueprint cannot reference itself.
- **No identity, no mutation.** `[Context]` has no `BaseContext` intersected in (`CommandContextOf<Shape>` is just `{ [Key in CommandDomainKeys<Shape>]: Shape[Key]["prototype"] }`), there is no `id`/`createdAt`/`updatedAt` getter, and there is no `set`/`setMany` — a `Command` that needs to change something calls a business method on the `Entity` it orchestrates inside `execute()`, never mutates itself.
- **`execute(deps): Promise<CommandResult<Result>>` is `abstract`, alongside `defineCommand`.** It is the *only* place I/O or side effects belong — construction stays synchronous and fails fast on bad input (schema validation happens in each `ValueObject`'s own constructor, same as `Entity`), so `Deps` (repositories, external services) only ever reaches the subclass through `execute`'s parameter, never the constructor.
- **`CommandResult<Result> = { readonly result: Result; readonly events: readonly IDomainEvent[] }`.** `events` is always an array, never `undefined`, mirroring what `Entity.pullDomainEvents()` itself returns. `Command` never publishes anything on its own — `execute()` only *surfaces* the events, leaving when/how to publish to whoever called `execute()`. This is also why `Command` has no `[Events]` slot or `raiseEvent` of its own: only an `Entity` (the aggregate root) may raise a domain event, per its own `raiseEvent` being `protected`; a `Command` can only *collect* what an `Entity` it touched already raised.
- **`collectDomainEvents(...aggregates)`** (a public helper in `application/command/helpers`) drains one or more `{ pullDomainEvents(): readonly IDomainEvent[] }`-shaped buffers and concatenates them in call order — typed structurally, not against the concrete `Entity` class, matching the rest of the package's preference for structural discrimination over `instanceof`. The typical `execute()` body: call a business method on the entity (which may call `raiseEvent` internally), persist it, then `collectDomainEvents(entity)` to hand the drained events back in the `CommandResult`.
- **`collectResult(result, ...rest)`** is `collectDomainEvents`'s one-call sibling: it builds the whole `CommandResult<Result>` — `{ result, events: collectDomainEvents(result, ...rest) }` — from the aggregate `execute()` is returning as its result, collapsing the two-line pattern above. Same structural bound as `collectDomainEvents` (`Result extends { pullDomainEvents(...): readonly IDomainEvent[] }`), for the same reason: a concrete `Entity<Shape>` is not structurally assignable to a nominal `Entity<PropertiesShapeBase>` bound (its `toJSON()`/`get()` return types are shape-dependent), the same incompatibility `EntityConstructor` already sidesteps for the lifecycle decorators' mixin base (see "Lifecycle decorators" above) — a structural bound accepts any real entity subclass without hitting it. Reach for `collectDomainEvents` directly when the `Command`'s result isn't itself an aggregate (a `string`, `null`, …) or when more composition is needed than a single result plus extra aggregates.
- **`X.demo()`/`X.fromJSON(row)` work exactly like `Entity`'s.** `demo()` is `Reflect.construct(this, [Demo])`, same sentinel, same `noThisInStatic` biome-ignore requirement; rules resolve the same way in demo mode, so a `Command` fixture stays coherent. `fromJSON` validates the *whole* payload against the aggregate schema first (`additionalProperties: false`, rejecting missing **and** extra keys with `InvalidDomainDataException`) before constructing — the entry point for payloads of untrusted origin (an HTTP request body, say), same contract as `Entity.fromJSON`.
- **The construction machinery lives in `application/command/helpers/`, not inline in `command.ts`.** Unlike `Entity`'s `buildContext`/`buildProperty`/`modelFor` (forced to stay inside `entity.ts` to avoid a circular import through `isEntityClass`), `Command`'s versions never need to import `Command` itself — a value-object-only blueprint has nothing to discriminate — so they're ordinary internal helpers, each in its own file, mirroring the "one thing per file" convention more closely than `Entity` is able to.
- **`rulesOf`, `applyRuleDefaults` and `installAccessors` come from `@/shared/helpers`, shared with the entity pillar.** They used to be duplicated per pillar, on the grounds that reaching into `domain/entity/helpers` would cross a barrel boundary — but all three are byte-identical in behaviour, so the copies only guaranteed that a fix to one would silently miss the other. `installAccessors` in particular was documented as differing "in the nested-entity branch of the getter"; **it never did** — the getter is `return this.get(key)` in both, and the nested-entity branch lives in `Entity.get`, which is where it belongs. Its only real difference was the pillar name quoted in the collision message, now a `label` parameter. `readDefinition` stays duplicated per pillar on purpose: its identity *is* the method name it probes (`defineEntity` vs `defineCommand`) and the message explaining the class-field trap, so parameterising it would trade duplication for indirection with nothing gained. Contrast both with `blueprint`/`RulesOf`/`PropertyRule`/`RuledBlueprint`/`BlueprintBuilder`, which are imported straight from `@/domain/entity` — already public, and generic enough to accept `Command`'s narrower shape unmodified.
- **Validation failures are re-tagged `application`-layer at the command's own boundary; definition-time mistakes stay `domain`-layer.** `defineCommand`'s class-field guard reuses `InvalidEntityDefinitionException`, the blueprint-key collision guard reuses `PropertyNameCollisionException`, and `get()`'s unknown-key guard reuses `InvalidPropertyException` — the same `domain`-layer exceptions `Entity`/`ValueObject` already use for the identical class of mistake, because none of these are about untrusted input crossing a boundary; they're bugs in how the class or the call site is written. But a **raw value failing validation during construction** is different: `buildProperty` (`application/command/helpers/build-context.ts`) `try`/`catch`es the `ValueObject`'s own `InvalidPropertyException` and re-throws `UnprocessableContentException` (422, from `@roastery/terroir/exceptions/application`), wrapping the original as `cause` — the property is still validated by ordinary domain machinery, but the *failure* belongs to the application layer, since it was the command's input that was wrong, not a domain invariant. `fromJSON`'s whole-payload schema mismatch (missing/extra keys) throws `BadRequestException` (400) the same way, replacing what would otherwise be `Entity.fromJSON`'s `InvalidDomainDataException`. Both `ApplicationException` subclasses fix `[Layer]` to `"application"` (from `@roastery/terroir/symbols`, sealed by the abstract base) — the whole point of the split: error-handling middleware reading `error[Layer]` can tell "this command's own input was invalid" apart from "a deeper domain invariant broke," which a uniform `domain`-layer exception could not distinguish.

### commandOf, AggregateCommand, aggregateCommandOf, defineUseCase

`entityOf`'s pattern repeats twice more in this pillar — once for `Command` itself, once for its single-aggregate specialization:

- **`commandOf<Shape, Deps, Result>(properties, source, extra?)`** (`application/command/helpers/command-of.ts`) is `entityOf`'s twin: returns a `Command` base already bound to the blueprint via `BoundCommand` (`command.ts`, not exported from any barrel), so the subclass owes only `execute()` — no `defineCommand()`, no `interface X extends CommandAccessorsOf<…> {}` merge. `BoundCommand.defineCommand()` reads a `static readonly definition` the factory stamps onto the generated class, via `readBoundDefinition` (`helpers/read-bound-definition.ts`). `CommandClassOf<Shape, Deps, Result>` (`types/command-class-of.type.ts`) is the returned shape — `abstract new`, since `execute()` is still owed — for the same TS4060 reason every class-returning factory here annotates its return.
- **`AggregateCommand<Shape, Deps, Result>`** (`application/command/aggregate-command.ts`) specializes `Command` for the case its own docs already name but leave manual: the result is a single aggregate, and `execute()`'s last line is always `return collectResult(result)`. Here `execute(deps): Promise<CommandResult<Result>>` is concrete (inherited, not abstract) and calls `collectResult(await this.handle(deps))` — the subclass implements `protected abstract handle(deps: Deps): Promise<Result>` instead, returning the aggregate on its own. `Result` carries the exact structural bound `collectResult` already declares (`{ pullDomainEvents(...): readonly IDomainEvent[] }`), duplicated inline rather than factored into a shared type, matching how `collectDomainEvents`/`collectResult` already duplicate it between themselves. `handle` is `protected` — `execute()` stays the one public verb, the same reasoning that keeps `Entity.raiseEvent` protected. One inference nuance, harmless: because `execute`'s parameter is always named here (it forwards to `handle(deps)`), a `Deps = void` command built on `AggregateCommand` resolves through `DepsOfClass` as `void` rather than the `unknown` a hand-written parameter-less `execute()` infers — `RegistrableKeys`/`DirectlyRegistrableKeys` already treat both outcomes identically (see "CommandRegistry usage" below), precisely for this.
- **`aggregateCommandOf<Shape, Deps, Result>(properties, source, extra?)`** (`helpers/aggregate-command-of.ts`) is `commandOf`'s counterpart for `AggregateCommand` — same blueprint-binding trick, via `BoundAggregateCommand` (also in `aggregate-command.ts`, also not exported from any barrel), so the subclass owes only `handle()`. `AggregateCommandClassOf` (`types/aggregate-command-class-of.type.ts`) is `CommandClassOf`'s counterpart. `readBoundDefinition` is shared by both `BoundCommand` and `BoundAggregateCommand` — both implement the exact same "read the factory-stamped static, or explain how to fix it" `defineCommand()` logic, differing only in which factory name (`"commandOf"` vs. `"aggregateCommandOf"`) the guard's message suggests.
- **`defineUseCase<Shape, Deps, Result>(properties, source, extra?)`** (`helpers/define-use-case.ts`) is a thin, friendlier-named entry point onto `aggregateCommandOf` — same class, same behaviour, delegates outright, for a consumer who doesn't need the DDD vocabulary the rest of this pillar is precise about on purpose. It is also the one `application/command` name re-exported from `@roastery/beans/way` (see "Architecture" above) — `commandOf`/`aggregateCommandOf`/`Command`/`AggregateCommand` stay reachable only through their own subpath, as the escape hatch.

### CommandRegistry usage

`commandRegistry(spec).withDependencies(dependencies)` gates `.get(key)` to only the commands in `spec` whose declared `Deps` `dependencies` structurally satisfies — resolved entirely at compile time.

```ts
const registry = commandRegistry({
	createUser: CreateUserCommand, // Deps = { secrets; users }
	renameTag: RenameTagCommand,   // Deps = void
}).withDependencies({ secrets, users });

await registry.get("createUser")(payload); // constructs + execute()s in one call
```

- **Two-phase for the same reason `blueprint` is.** A literal cannot reference its own `typeof`, so `Spec` is fixed by the `commandRegistry(spec)` call before `withDependencies`'s `Dependencies` can be checked against every spec member's `Deps` in the second.
- **`.get(key)` returns a ready-to-run bound function, not the class and not an unexecuted instance.** It constructs the command with the payload and immediately calls `.execute(dependencies)` on it, resolving to the same `CommandResult<Result>` `execute()` itself returns.
- **The gate is compile-time only — `Command` is not modified.** `Deps` has zero runtime footprint (no symbol slot, unlike `Properties`/`Context`/`Source`), so "only registrable if its dependencies are present" can only exist as a type-level constraint: `RegistrableKeys<Spec, Dependencies>` maps every spec key to itself-or-`never` (the same `UndefinedableKeys`-style "map then index-collapse" idiom `domain/entity/types` already uses) and collapses to the union of keys `.get()` accepts. A caller who bypasses TypeScript (`as never`, plain JS) faces no runtime check — `execute()` just receives whatever `dependencies` was, missing keys and all.
- **`Deps = void` has two different `infer` outcomes, and the gate has to handle both.** Every no-deps command in this package elides `execute`'s parameter entirely (`public async execute(): Promise<CommandResult<X>>`) rather than writing `execute(deps: void)` — and eliding it means `DepsOfClass`'s `infer` has no parameter position to constrain against, so it resolves to `unknown`, not `void` (TypeScript's contravariant-inference fallback is the top type). Only the explicit `execute(deps: void)` form resolves to `void` itself. `RegistrableKeys` special-cases both (`unknown extends DepsOfClass<...>` and `DepsOfClass<...> extends void`), since either means "reads nothing from `execute`'s argument" and must be registrable regardless of what `Dependencies` is.
- **The check is structural, not exact — the same limitation `Command.execute` already has.** `execute` is method shorthand (matching `ICommand`), and TypeScript exempts method shorthand from `strictFunctionTypes`'s contravariant parameter checking (deliberately, for OOP covariance). A `Dependencies` record whose nested method-shaped member is only bivariantly compatible with what a command's `Deps` declares can satisfy `RegistrableKeys` without truly being a safe substitute. Not fixable from inside `command-registry/` without changing `Command`/`ICommand` itself, which is out of scope — documented, not engineered around, matching the "nothing stops a caller who bypasses TypeScript" stance already taken for the gate itself.
- **`AnyCommandClass` is built entirely from `application/command`'s already-public surface** (`CommandResult` alone, from `@/application/command/types`) — no reach into that pillar's internals. `DepsOfClass`/`ResultOfClass`/`PayloadOfClass` all recover their target type via `infer` on the concrete class substituted for `AnyCommandClass`'s `never`-bounded `execute`/constructor slots, the same "widest structural bound, recover specifics via `infer` later" idiom `AnyValueObjectClass`/`AnyEntityClass` already use.
- **An unknown key at runtime throws `InvalidPropertyException`**, reusing the same exception `Command.get()` already raises for its own "key the blueprint never declared" guard — same class of mistake, `source` fixed to `"command-registry"` since there is no per-instance `[Source]` here the way there is on a `Command`.
- **A runtime guard backs the compile-time gate, independently of it.** `RegistrableKeys` still only *proves* one hop; the `commands` bag it feeds stays unlimited in depth (unchanged), so `withDependencies` now builds it via a `buildCommands(spec, dependencies, chain)` recursion instead of one flat shared object — `chain` is a `ReadonlySet<string>` of command keys already on the current call chain, threaded fresh (not mutated) into every nested `execute()`'s own `commands`. A key that shows up again in its own chain throws `LoopDetectedException` (HTTP 508, from `@roastery/terroir/exceptions/application`) instead of recursing until the stack overflows. The chain is rebuilt per call rather than tracked in one shared, mutable `Set` (the `deriving`/`constructing` pattern `domain/entity` uses for blueprint cycles) specifically because `execute()` is async: a shared mutable guard cannot tell two unrelated *concurrent* calls to the same key apart from a real cycle, since the first call's in-flight marker would still be set when the second, unrelated call checks it. Two sibling calls to the same key from different branches of a chain — not nested inside one another — correctly stay unflagged, the same "siblings, not a cycle" distinction the entity guard already draws.

### Custom VO factories

`domain/collections/value-objects/custom/` ships functions that **return a VO class**, so a blueprint can carry a constraint inline instead of a schema plus a subclass per rule. Subpath: `@roastery/beans/domain/collections/value-objects/custom` (types one level deeper, under `/types`; also reachable, unchanged, via the `application/collections/value-objects/custom` alias). `defineValueObject({ schema, default, name?, transform?, validate? })` is the core; `customStringVO`, `customNumberVO`, `customArrayVO(items, args?)`, `customObjectVO(properties, args)`, `customRecordVO`, `customEnumVO(values, args?)`, `optionalVO(schema, args?)` and `nullableVO(schema, args?)` are thin wrappers that only build the schema and delegate.

This works because the blueprint machinery is **entirely structural** — `isEntityClass` is `prototype instanceof Entity`, `SchemaOf` infers through `ValueObject<unknown, infer SchemaType>`, `RawValueOf` reads `prototype["value"]`, and nothing in `src/` ever touches `Class.name`. A class expression satisfies `AnyValueObjectClass` and lands in the VO branch on its own.

- **Every factory must annotate its return type with `ValueObjectClassOf<V, S>`.** The class is declared inside the function body, and `tsconfig.build.json` sets `declaration: true` while `bun run build` runs `tsup --dts` — an inferred return type fails with **TS4060** (`Return type of exported function has or is using private name`) and emits no `.d.ts`. The `as ValueObjectClassOf<…>` on the return covers `demo` alone: the base declares it generic over `this`, so assignability instantiates `Self` at its constraint and the return collapses to `{ value: unknown }`.
- **Call the factories at module scope, once.** Each call mints a fresh schema object *and* a fresh class. `SchemaManager` caches compiled validators by schema identity and `modelFor` memoizes by blueprint object, so a factory called inside `defineEntity()`/`defineMeta()`/`defineCommand()` recompiles per construction — silently, only slower. Corollary: two calls with identical arguments produce unrelated classes, so `instanceof` does not connect them.
- **The schema and the `meta` literal live in the closure, never in the class body.** `defineMeta()` runs on every construction; building either inside would allocate per instance and hand `SchemaManager` a new cache key each time.
- **Ready defaults are validated eagerly, inside the factory call**, raising `InvalidEntityDefinitionException` (with `name` as its `source`, falling back to `"value-object"`). That turns a latent `demo()`/blueprint failure into a module-load failure. **Thunk defaults are skipped** on purpose — checking one would evaluate it, defeating the laziness — and the base still validates them at demo time.
- **`customObjectVO` requires `default`**; there is no placeholder for an arbitrary set of required properties, and `Value.Create` is out of reach (terroir re-exports only the root `@sinclair/typebox` module, not `/value`). The others fall back to `"string"` / `0` / `[]` / `{}` / `values[0]`, each then subject to the eager check.
- **`customEnumVO` infers its literal tuple through a `const` type parameter**, so the caller's array of values does not need `as const`. It builds the schema with TypeBox's own `t.Enum`, not a hand-rolled `t.Union` of `t.Literal`s — the record's keys (stringified values) are thrown away, since `t.Enum` only reads the record's *values*.
- **`optionalVO` wraps an existing schema in `t.Union([schema, t.Undefined()])`**, so the generated VO's value may be `undefined`. This is the only sanctioned way to get an `undefined`-accepting VO: the base `ValueObject`'s `ValueType` was never constrained against it, but nothing validated it either until the schema itself says so. Its default, when omitted, is `undefined` — not a placeholder that then needs validating. A blueprint property backed by one **is an omittable key** in the constructor payload's type (`UndefinedableKeys` in `domain/entity/types`, see above) — `Entity`'s runtime already read a missing key the same as an explicit `undefined`, so the type only had to catch up.
- **`nullableVO` wraps an existing schema in `t.Union([schema, t.Null()])`**, so the generated VO's value may be `null`. Its default, when omitted, is `null`. Unlike `optionalVO`, a blueprint property backed by one is **never** an omittable key — `null` doesn't extend `undefined`, so `UndefinedableKeys` doesn't pick it up, and the caller must state `null` explicitly (`new Post({ deletedAt: null })`, not `new Post({})`). Reach for `optionalVO` when a property may not have been provided, `nullableVO` when it was provided and is explicitly empty — the usual `undefined` (request body) vs. `null` (database column) split.
- **`validate` is a predicate**, not a `void` hook: it runs *after* `super.validate()`, so it only sees transformed, schema-valid values, and returning `false` raises `InvalidPropertyException` with the context's `name`/`source`. Throwing from inside works too and propagates untouched.
- **The barrel carries `import "@roastery/terroir/schema/formats"`** — without it, `customStringVO({ options: { format: "slug" } })` would validate against an unregistered format. Only `domain/collections/schemas/index.ts` did this before.
- **`options` stays nested** in the args (`{ options: { minLength: 4 } }`), not spread. TypeBox's `SchemaOptions` already declares a `default` field — the JSON Schema annotation — which means something else entirely from the demo-mode fallback.

**Aggregates.** A blueprint value may be a `ValueObject` class **or another `Entity` subclass**. The discriminant is `toJSON` at the type level and `prototype instanceof Entity` at runtime. (This is `Entity`-only — a `Command` blueprint never has this branch; see "Command subclass" above.)

- `get("author")` returns the **nested instance** (chainable: `post.get("author").get("name")`); `set("author", raw)` takes the nested entity's *raw* payload — identity optional, same all-or-nothing rule — and rebuilds it.
- `toJSON`/`fromJSON`/`schema` all recurse.
- A validation error raised inside a nested entity carries **its own** `source` and field name (`("name", "author")`, not `("author", "post")`) — more precise, but the outer path is lost.
- Mutating a nested entity directly (`post.get("author").set(...)`) does **not** stamp the parent's `updatedAt`; only `post.set("author", raw)` does.
- **Cycles are detected, not survived.** A blueprint `A → B → A` recurses in two independent places — schema derivation and construction — and both are guarded by a set of in-progress blueprints, so you get a `CyclicEntityDefinitionException` naming the entity instead of a bare `RangeError`. The guard releases on the way out, so two properties of the *same* entity class in one blueprint (siblings, not a cycle) keep working. The cycle still has to be broken; the guard only makes it diagnosable.

## Conventions

- **The `biome-ignore` comments on `demo`/`fromJSON` are load-bearing**: `biome check --fix` (which `bun run build` runs) classifies `noThisInStatic` as a *safe* fix and would rewrite the `this` in those statics into the abstract base class, making them build the base instead of the subclass. Keep the directives verbatim (`domain/entity/entity.ts`, `domain/value-object/value-object.ts`, `application/command/command.ts`).
- **Never declare a slot symbol locally.** All eight terroir-owned slots (`Context`, `Demo`, `Events`, `Meta`, `Properties`, `Rules`, `Source`, `Storage`) come from `@roastery/terroir/symbols`. `Properties` and `Source` are used as type-level keys (`Instance extends { [Properties]: infer Shape }`), so a second symbol with the same description — or a module-local redeclaration — would make those conditional types silently stop matching, and every slot read return `undefined`. `grep -rn 'Symbol("' src` must return **zero** hits: `src/events.symbol.ts` (the temporary home of `Events`, mirroring `src/entity/rules.symbol.ts` before it) is gone now that terroir 0.2.1 ships the symbol. Do not reintroduce one. `Command` introduces no ninth symbol — it reuses four of the existing eight (`Context`, `Demo`, `Properties`, `Source`) and needs none of the other four (no `Events`/`Storage`/`Rules` slot of its own, and `Meta` belongs to `ValueObject`).
- **A symbol used as a computed key is a *value* import, not a type import.** `Rules` appears in both positions and the distinction is load-bearing: `ruled-blueprint.type.ts` and `ruled-keys.type.ts` only ever mention it inside a type (`{ readonly [Rules]: Rule }`) and correctly use `import type`, while `blueprint.ts` and `rules-of.ts` *read and write* the slot at runtime (`properties[Rules]`, `Object.assign({}, properties, { [Rules]: rules })`) and need a plain `import`. Because `verbatimModuleSyntax: true` erases `import type` outright, getting this backwards does not fail at the import — it throws `ReferenceError: Rules is not defined` from inside `buildContext`, so *every* entity (or command) construction breaks at once while the module graph loads fine. `application/command/types/command-ruled-keys.type.ts` draws the same line for its own copy: `import type { Rules }`, since it only ever appears inside a type there too.
- **What `application/command` shares with `domain/entity`, and what it keeps of its own, is a three-way split — deliberate, not inconsistent.** *Shared through `src/shared/helpers/`* (behaviourally identical in both pillars): `installAccessors`, `applyRuleDefaults`, `rulesOf`. *Imported straight from the domain pillar* (already public, already generic enough): `blueprint`, `RulesOf`, `PropertyRule`, `RuledBlueprint`, `BlueprintBuilder`. *Duplicated on purpose*: `readDefinition`, whose whole content is the pillar-specific method name and message, and the types `DomainKeys`/`AnyValueObjectClass`/`RuledKeys`/`UndefinedableKeys` (under `Command*`-prefixed names), which describe a narrower blueprint shape. See "Command subclass" for the reasoning.
- **One intentional naming pair**: `EntityStorage` is the runtime class (`domain/entity/entity-storage.ts` — internal, not re-exported from any barrel), `Storage` is the symbol keying its per-instance slot (`@roastery/terroir/symbols`).
- **Reach for the specific domain exception, not the generic one.** terroir 0.2.0 ships `ImmutablePropertyException`, `PropertyNameCollisionException`, `IncompleteIdentityException`, `InvalidEntityDefinitionException` and `CyclicEntityDefinitionException` — added because *this* repo was collapsing all five cases into `OperationFailedException`/`InvalidPropertyException`. Tests assert the class (and the `property`/`source` slots), never a message substring. Every exception also takes a trailing `ErrorOptions`, so a wrapped failure keeps its `cause`. `application/command` reuses these same domain-layer exceptions for its own definition-time mistakes (`defineCommand` as a class field, a colliding blueprint key, `get()`'s unknown-key guard) — the same class of error `Entity`/`ValueObject` already use them for. It reaches for terroir's `ApplicationException` catalog (`UnprocessableContentException`, `BadRequestException`) only where a `Command`'s own *input* fails validation — re-tagging what would otherwise be a domain exception as it crosses the command's boundary, `cause` preserved. See "Command subclass" for the exact split. `src/testing/` is the only place reaching terroir's `InfraException` catalog (`ConflictException`, `ResourceNotFoundException` from `@roastery/terroir/exceptions/infra`) — an adapter's failures belong to the infra layer, and the in-memory double is the one adapter in the package. Note `ConflictException` carries no `property` slot (only `source`/`message`), so a test can assert the class but not which key collided; the fix, if that ever matters, is asking terroir for the slot, exactly as the five domain exceptions were added — not subclassing locally.
- **`tsconfig.json` has `verbatimModuleSyntax: true` and `strict: true`.** Type-only imports must use `import type`; mixing types into value imports breaks the build.
- **Re-exports are explicit (`export { X } from "..."`), not `export *`.** Barrels are sorted alphabetically.
- **TSDoc is mandatory** on every non-test source file, in **English** — descriptions + `@param` + `@returns` + `@throws` + `@typeParam` + `@example` + `@see`, with `@module` (or `@packageDocumentation` for the root) on every barrel. Runtime error messages are English too.
- **Never type-check a scratch file whose name starts with a dot.** TypeScript's default `include` (`**/*`) does not match dotfiles, so `tsc --noEmit` exits 0 while silently ignoring `.probe.ts` / `.spike.ts`. A design spike was once declared sound on exactly that false signal; the same file renamed without the dot failed immediately with TS2515. Use a plain name (`probe-check.ts`) and delete it afterwards.
- **Don't use `any` in tests.** Stay strict with the real types (rule from `.agent/rules/dont-use-any-type.md`).
- **`bun:test` is the only testing framework** (rule from `.agent/rules/use-bun-test.md`).

## Agent context (`.agent/`)

`.agent/` is a git submodule of the Caffeine.js Agent Guide reused here as the Roastery agent context. It contains shared rules (`.agent/rules/*.md` — language style, no-`any` in tests, `bun:test`, Biome guidance) and workflows (`.agent/workflows/*.md` — `smart-commit`, layered review workflows). Note the rules occasionally reference `@caffeine/*` packages — the closest equivalents in this repo are `@roastery/beans/domain/entity/helpers` (`blueprint`, `deepEquals`, `generateUUID`) and, for application-layer orchestration, `@roastery/beans/application/command/helpers` (`collectDomainEvents`). The rules also mention entity factories, which this package no longer ships: fresh identity comes from the `Entity` base itself, and fixtures from `X.demo()` (or, for a `Command`, the same `X.demo()` static).
